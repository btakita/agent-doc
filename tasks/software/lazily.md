Done, across ten repos. The clause is normative, the audit is in protocol.md, the fixture is replayed by all nine bindings — and it found two real defects in lazily-cpp on its first run.

**The clause.** protocol.md § NodeId / PeerId now carries a decoder obligation beside the producer bound: *a decoder that cannot represent a received `NodeId`/`PeerId` exactly MUST reject the frame; it MUST NOT round, truncate, saturate, or wrap.* The producer bound was also reworded as you asked — it names the constraint (a runtime whose integers are IEEE-754 doubles, which is every JavaScript target *including* Dart, Kotlin, and TypeScript compiled to JS) instead of the source language. The old "JavaScript/TypeScript peers" phrasing read as a source-language rule and left compiled-to-JS peers apparently exempt.

I also fixed a contradiction the audit surfaced: `schemas/defs.json` capped `PeerId` at 2^53−1, which made a legal `u64` frame schema-*invalid* and pushed a runtime-capability question into wire validity. Both `NodeId` and `PeerId` are now u64-wide in the schema; refusal is a decoder decision, not a validity one.

**The audit — all nine, empirically, not by reading.**

| Binding | Identity type | Exact range | Outside it |
|---|---|---|---|
| rs | `u64` | full `u64` | serde error |
| zig | `u64` | full `u64` | `error.Overflow` (`std.json` yields `.number_string`; `parseInt(u64)` refuses) |
| cs | `ulong` | full `u64` | `FormatException` |
| py | `int` | unbounded | n/a — nothing to round to |
| go | `int64` | `[0, 2^63)` | unmarshal overflow error |
| kt | `Long` | `[0, 2^63)` | `NumberFormatException` / `MsgpackCodecException` |
| cpp | `int64_t` | `[0, 2^63)` | **was substituting — fixed** |
| js | `number` | `[0, 2^53)` | `TypeError` (`Number.isSafeInteger`, both codecs) |
| dart | `int` | `[0, 2^63)` VM / `[0, 2^53)` web | `UnsupportedError` (`#lzdartintwidth`) |

Two corrections to the item's premise. **lazily-dart no longer accepts** — `#lzdartintwidth` landed a deliberate platform-split refusal in `lib/src/int_width.dart`, so that half is stale. And the interesting result is not the table but *how* the seven unaudited bindings got there: only js and dart carry the rule deliberately. The other seven inherit it from a parser that happens to fail closed, which is a property nothing held in place — and two lazily-cpp decoders did not hold it:

- `MsgUnpacker::read_i64` cast a msgpack `uint 64` straight to `int64_t`. `u64::MAX` decoded as `-1` — a well-formed identifier for a different node, no error anywhere. This is exactly the silent substitution the clause forbids, and it was invisible to source reading because I'd only checked the JSON parser.
- `json_parse` *did* refuse an over-range integer, but by letting `std::stoll` throw `std::out_of_range` — a `std::logic_error`, not the `std::runtime_error` every other parser failure raises and every caller guards a decode with. The exception escaped the decode boundary entirely.

Both fixed; the C++ runner asserts the refusal through `std::runtime_error` *specifically*, since catching `std::exception` would have passed against the broken parser.

**The fixture.** `conformance/codec/nodeid_exact_range.json` — 2^53−1, 2^53+1, and `u64::MAX`, in both codecs, generated by `scripts/gen_nodeid_exact_range_fixture.py`.

Two design points worth recording, because both are traps:

1. **The fixture cannot carry its own expectation as a JSON number.** The fixture is JSON. A bare `9007199254740993` in it gets rounded by the parser *loading the file* on any double-backed runtime — so the runner would compare a rounded expectation against a rounded decode and pass against precisely the decoder it exists to catch. Wire frames are therefore raw text (json) and hex (msgpack), and the expectation is a decimal *string*. A spec-side guard walks the parsed fixture and fails on any integer above 2^53−1 appearing anywhere as a number, so the rule can't rot.
2. **The outcome can't be one boolean**, because the correct answer differs per binding. Scenarios are `exact` or `exact_or_reject`. But `exact_or_reject` alone is satisfied by a runner that decodes nothing and calls everything refused — so the 2^53−1 scenarios are `exact` controls every binding must decode, and each runner pins its accept/refuse **counts exactly** rather than "at least one". A guard that stops refusing and a decoder that stops decoding are each a failure.

**Nine runners, not a deferral.** Dropping the fixture into the corpus immediately failed all nine `check-conformance-coverage.sh` guards — they read the canonical corpus directly, so "land the spec now, adopt later" was never available. Each binding got a runner, its build/test registration, and where the script keeps one, a `MIN_FIXTURES` bump. `coverage.json` carries a new row, verified by `check-coverage-claims.mjs` against each binding's own runtime ledger. Every runner was mutation-checked — corrupting the fixture's expected identifier reddens each one, and deleting lazily-js's `Number.isSafeInteger` guard reddens its runner with "the identifier was ROUNDED to a neighbouring node id".

**Verification.** `make check` green in all ten repos. CI green on lazily-spec, js, kt, go, zig, cpp, dart, cs; rs and py still in progress at write time on the format/CI-reach follow-up commits (both green locally). Landing this needed two CI-only fixes: lazily-rs's `ci-reach` guard demanded a CI step for the new `make check` target, and lazily-py's `ruff format` / lazily-dart's `dart analyze --fatal-infos` rejected the new files.

One thing I did **not** do: nothing here widens a binding's identity type. The clause explicitly permits a narrower exact range, so go/kt/cpp keeping `int64` and js keeping `number` are conforming — they refuse rather than substitute, which is the whole point.
