|---|---|---|
| `preflight::enforce_cycle_completion` | `pending_document_write(file).is_some()` — a fresh `load_state_backbone_projection` SQLite replay at the decision seam | unsettled → bail |

### Re: Can EditorSurfaceState be decomposed into reactive primitives? — opus-5

It already is three, and asking the question found a bad test. Taking the parts separately:

**It is `Source` + `Computed` + `Effect` today.** `ThreadSafeStateMachine` is not a fourth primitive — it is a `Source<S>` plus a pure `Fn(&S, &E) -> Option<S>`. So the graph is one source cell holding the fold, one computed cell over its state handle, and one effect gated on that. There is no further decomposition in the sense of "swap this for smaller pieces".

**The history cannot decompose into `Computed`s, and shouldn't.** `reconciled_signature` and `focused_document` are *the last observation that produced a consequence*. That is a fold over the stream, and a `Computed` cannot read its own previous value — so the only way to split them is to write two `Source`s by hand from the observation. That is precisely the `idle_revision.rs` regression `AGENTS.md` records: the first draft wrote three sources by hand from one method and shipped two ordering bugs, a baseline advanced in the tick it was compared against and a baseline that lagged two observations. Splitting here would reintroduce that class, not remove it. The compound `SurfaceFold` is what makes the ordering unwritable.

**The genuinely available decomposition is one I decided against.** `visible_signature` and `is_inert` are pure functions of the *current* observation, so they could be `Computed`s over an observation `Source`. But `advance` already receives the observation by reference and computes the signature once per event, so hoisting them buys memoization of a string nobody reads twice, at the cost of a second cell that must be written in step with the machine. Not worth it.

**The part that should be a different primitive is the intent, and lazily can't express it yet.** An intent is an *event*, not a state, and I am storing it in a state cell — which is why `SurfaceFold` needs an `epoch` counter at all. The correct primitive is a stream: derive the intent, publish it to a `QueueCell`/topic, drain it in the effect. Then two identical consecutive intents are two events and the counter disappears. I did not do it because `QueueCell` is `Rc`-based and single-threaded, and this plane is thread-safe (observations arrive on editor threads). There is no thread-safe queue in the family today. So the epoch stays as the honest workaround, and the comment says so.

**And the test that was wrong.** I had a test named `an_identical_intent_derived_twice_still_fires` justifying the epoch. Your question made me mutation-check it: with the epoch bump deleted, **all 15 tests still passed.** The scenario it used (two columns → one → two) is already caught by the ordinary equality guard, because the guard compares against the immediately previous value, not a historical one. The shape that actually needs the epoch is two *consecutive* observations folding to an identical value with a non-idle intent — pressing Sync Tmux Layout twice, or tmux reporting drift twice. Without the epoch the guard swallows the second press and nothing happens. Both new tests fail with the field neutralized and pass with it, and the old one is kept under an honest name that says the guard already covers it.
