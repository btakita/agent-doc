In the EFS `tasks/professional/equityfundingsource.md` agent-doc session (and any doc with `queue: stop` frontmatter + an `<!-- agent:queue preset="#..." -->` block), each cycle the user replaces the queue body with a new free-text prompt. Two recurring, harmless quirks:

1. **`finalize` often exits 75** with `invariant=prompt_duplication_in_ack_content` (or `live_prompt_drift_after_preflight` / `missing_response_probe`), then the `content_ours` / CRDT-merge fallback commits the FULL correct response to HEAD anyway. Always verify after: `session-check` final line says `committed (commit_success)`, `git show HEAD:FILE | grep -c "<response heading>"` == 1, and `git status --short FILE` is clean (no post-commit worktree drift). If clean, it's done — do NOT re-run the response cycle.

2. **The answered free-text queue head does NOT auto-strike** (the exit-75 path skips consume), and `agent-doc queue consume FILE --count N` REJECTS it with "queue head is an id-backed directive" — a misclassification caused by the `preset="#spec-test-commit-push"` token on the queue. The leftover item is cosmetic only: `agent-doc preflight` reports `no_changes: true` (the item is committed into the snapshot, so it never re-fires). The user clears it themselves by editing the queue next cycle.

**Why:** wastes a recovery loop if you treat exit 75 as failure, and wastes effort fighting `queue consume`.

**How to apply:** after finalize, run the 3-line HEAD/worktree/session-check verification; if HEAD is correct + tree clean, report success and stop. Don't re-finalize, don't manually edit the queue, don't fight `queue consume`. Mention the leftover line is harmless. This is an agent-doc bug worth filing in the `agent-doc-bugs2.md` session (NOT from the EFS session — see [[feedback_session_document_scope_discipline]]) if it keeps recurring. Related: [[feedback_post_commit_worktree_drift_checkout_head_recovery]], [[feedback_ipc_crdt_response_loss_forcedisk_recovery]].

**Update 2026-06-19 (agent-doc 0.34.14, EFS session, `queue: start`/go):** `agent-doc queue consume <FILE>` now SUCCESSFULLY drains the answered free-text preset-token head (`consumed: "..." (remaining: 0) — drained, cleared queue_active`) — the old "consume rejects it" behavior is fixed for free-text heads. So the clean drain step after a committed response is: verify HEAD has the response heading, then `agent-doc queue consume <FILE>` → `session-check` shows `queue_continuation_required=false`. (Bare-preset-key heads like `#bugs-observed` may still be un-drainable — see go-mode variant below.) Also seen this session: `finalize` repeatedly failed with `IPC socket ack status error` + file-IPC `invariant=no_ack recovery=retry_without_disk_write` (NOT exit-75) because a concurrent idle-watch `supervisor_auto_install` (`cargo build --release` of agent-doc for a SIBLING dogfood doc) saturated CPU so the in-process apply missed its 2s window. The patch parses cleanly (`valid_patch`, `early_ack_pending`) and stays queued at `.agent-doc/patches/<hash>.json`; the supervisor applies it during a build gap, and the next `session-check` reports `committed (... commit_boundary_recovered)`. Recovery = do NOT direct-write; wait for the build to free the supervisor (poll `pgrep -f "cargo build --release"`), then verify HEAD + `session-check`. Re-finalizing just re-queues the same patch.

**go-mode variant is NOT harmless — it floods (confirmed 2026-06-13, tsift.md session).** When the queue is `go` (not `stop`) and a head is a bare preset key like `#bugs-observed` (a `prompt_presets` token used directly as a queue item), that head is fully un-drainable by the agent: `queue consume` rejects it ("queue head is an id-backed directive"), AND `agent-doc write --done bugs-observed` fails with `id not found in backlog/icebox: bugs-observed` (the `#`-prefix is misclassified as an id-backed directive but no such backlog id exists). In go-mode the supervisor idle-watch keeps re-dispatching it → flood. Recovery: do the work + verify HEAD committed + `git checkout HEAD -- FILE` for any post-commit worktree drift, then HALT the flood with `agent-doc admin queue pause <FILE> --observed-generation <N> --reason ...` (the first call prints `current_generation=<N>`; retry with that N). Do NOT auto-loop (session-check `queue_continuation_required=true` is moot once paused). File the un-drainable-preset-head bug for agent-doc-bugs2.
