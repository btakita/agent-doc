When preflight warns `stale_install` AND the JB plugin patch-apply IPC is wedged (`socket ack status:error` + file-IPC `nack_detail=file_apply_failed`, every finalize sticks at `response_captured`), do NOT blindly `make install`. First check whether the install is *actually* stale: compare `~/.cargo/bin/agent-doc` and `~/.cargo/bin/libagent_doc.so` mtime/version against the last COMPILABLE source. Here both were fresh (`0.34.67`, built minutes ago, JB pid-marker on the current `.so`) — the `stale_install` fired only because a **concurrent agent-doc refactor session left uncompilable WIP** in the submodule working tree (deleted `resync.rs`, a broken `?` in `agent-doc-sync-io/.../pane_repair.rs`) that is newer than the install. `make install` then FAILS to compile, so it cannot un-wedge anything, and the running (fresh but buggy) cdylib's apply path stays broken. This CONTRADICTS the usual [[feedback_jb_sigabrt_stale_cdylib_panic_abort_coredump_diagnose]] rule ("fix = make install") — that rule assumes the WIP compiles.

**Why:** the wedge is a regression in the *installed* build's file-apply path shipped by the concurrent refactor, not staleness relative to it. Nothing you can build is newer-and-working. Editor IPC AND `write --commit --force-disk` are both blocked: force-disk trips the buffer-differs guard because it injects a new pre-patch boundary into "expected disk" that the wedged plugin can never apply into its buffer (`visible editor buffer ... differs from the expected disk state`).

**The git-direct escape PERPETUATES the wedge via native-CRDT divergence (`#gitdirect-crdt-divergence`).** Each git-direct commit under a live JB editor changes disk without going through the plugin's native yrs CRDT node ops, so `MemoryDiskConflictResolver` keeps the in-memory buffer and the native node model's node-IDs drift from disk. The JB log then shows `PatchWatcher - native node-patch apply rejected patch_id … / Patch not applied, wrote nack + left file for retry` → CLI sees `nack_detail=file_apply_failed`. The buffer TEXT can be byte-identical to disk (same sha256, 0 lines differ) while node-patch still rejects — the mismatch is CRDT node identity, not text. `admin reload-lib` reloads the cdylib but NOT the per-document node model, so it does NOT fix it (confirmed: same `.so` that applied fine earlier keeps rejecting after divergence). There is NO CLI to rebuild the editor's per-doc CRDT (`sync`/`resync`/`fix` are tmux-layout only). The ONLY fix is the operator reloading the file in JB (File → Reload from Disk, or close/reopen the tab) — which is SAFE when buffer==disk (nothing unsaved to lose) and rebuilds the native CRDT from disk. Lesson: once you fall back to git-direct, STOP after the doc is correct in git; every extra git-direct commit deepens the divergence. Product-cause fix (agent-doc): the plugin must re-ingest external disk commits into the native CRDT instead of leaving it diverged and permanently rejecting node-patches.

**Read vs apply are separate IPC paths (do not conflate):** the JB live-buffer mirror's `last_synced_epoch` advancing (e.g. `0` → `538`) only proves the read/queue-convergence path recovered — it does NOT prove patch-apply healed. `file_apply_failed` can persist after the concurrent refactor commits its sync fix (`f3afce48`) and a fresh cdylib installs. Verify apply health with an actual `write --commit` attempt, not the epoch; if it still nacks, stay on the git-direct escape.

**How to apply:** (1) Confirm ownership is your own session, not a collision — `ps` your shell ancestry: `zsh → claude(2507926) → agent-doc start --route-owned <doc>(2507866) → pane %139`. `start --route-owned <doc>` + its child `claude` are YOUR wrapper, not a competitor (`admin detect` clean confirms). (2) Confirm disk is authoritative: the JB live-buffer mirror at `.agent-doc/live-buffer/<hash>.jetbrains-<pid>-...` carries a JSON `hash` field — if it equals `sha256sum` of the disk file (and lists `operator_text_authority_v1`), the buffer == disk with NO unsaved operator edits, so writing disk is safe. (3) Use the direct-write escape [[feedback_stale_binary_crdt_deadlock_direct_write_git_commit_reset]]: script-insert the response before the `<!-- agent:boundary:... -->` line (NOT the Edit tool — `❯` prompt markers are Read-tool annotations, absent from disk bytes), `git commit` the doc (git = durable truth even if JB autosave clobbers), then `agent-doc reset <FILE> --from-current` to rebuild snapshot/CRDT. Verify `git show HEAD:<doc> | grep <phrase>` and preflight `no_changes:true`. Do NOT `checkout HEAD` (discards the uncommitted operator prompt). Beware: a prior `--force-disk` may have already flushed a stale "pending retained" response (e.g. an old `### Re: deploy`) onto disk mis-placed after the newest prompt — keep it if true and append your real answer after it rather than fighting more force-disk churn.
