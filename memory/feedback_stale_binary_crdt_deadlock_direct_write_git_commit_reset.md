When a stale agent-doc binary/cdylib (preflight `stale_install` warning) corrupts the live CRDT, finalize/write can **deadlock**: the socket returns `already_applied` (so file-IPC fallback is skipped — "response already in live buffer") **while** `--force-disk` is blocked by `visible editor buffer differs from expected disk state`. The response never reaches disk or the operator's actual view (`disk_missing_response_probe`, `current_len` stuck at the prompt-only size). Moving the phantom `ipc.sock` + `crdt/<dochash>.*` + `state/cycles/<dochash>.json` aside then re-running finalize makes the **stale-base CRDT merge scramble the doc** (keeps only some response lines, drops headers, reorders before the prompt, auto-appends an `ipc_proof_insufficient` dogfood log). Verify a live IDE with `lsof <sock>` — a live `idea`/`agent-doc` PID means it's genuine corruption, not a dead endpoint.

**Why:** stale-cdylib corruption is not fixed by socket/state moves; every agent-doc write path re-corrupts because the running binary is old (see [[feedback_jb_restart_reopen_dont_fix_stale_cdylib_corruption]], [[feedback_stale_binary_supervisor_causes_live_crdt_edit_bugs]]).

**How to apply:** Stop fighting the CRDT. (1) Reconstruct the correct full document with the Write tool — preserve any real operator edits (e.g. a queue item added mid-recovery; check `lsof`/disk for live operator activity). (2) `git add <doc> && git commit` directly — git HEAD is the authoritative source of truth. (3) `agent-doc reset --from-current <doc>` to rebuild snapshot/CRDT from the committed disk. (4) Confirm with preflight `no_changes: true` / `staged snapshot already matches HEAD`. Then tell the operator to **reload the file in IntelliJ** (disk changed under the live buffer) and run `make install` to clear the stale binary. Root fix is `make install`; this sequence is the recovery when the response must land NOW. [[feedback_forcedisk_committed_but_false_closeout_error_stop_retrying]]

**2026-07-01 reitrades confirmation + nuances:** `make install` rebuilds the cdylib *file* but the **running JB plugin keeps the old cdylib in memory** — a JB **restart does NOT clear it because JB restores the unsaved (corrupt) editor buffer** (persisted `edit_epoch`), so the plugin re-scrambles every editor-path merge exactly as before (same `content_ours_len`, `live_prompt_drift`/`no_ack`/partial-apply). Recovery that worked: reset disk to clean HEAD → `agent-doc write --commit --force-disk` (this DID land the correct content on disk via CRDT merge, "no conflicts") → BUT its own commit refused with `live editor buffer has unflushed changes ahead of disk; refusing to commit from stale disk` → so `git add && git commit` directly + `reset --from-current --preserve-session`. Also: force-disk merging against the corrupt buffer left a literal ` (HEAD)` artifact appended to the response header (the boundary-marker annotation leaked into text) — strip it before committing. Operator MUST reload the file from disk in JB afterward or the stale buffer's next save re-corrupts the committed doc.
