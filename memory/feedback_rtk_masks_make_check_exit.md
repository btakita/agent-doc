When running `make check` (or `cargo test`) in agent-loop / `src/agent-doc`, the RTK hook rewrites the command through its digest-runner, which **captures output to a log but can return exit code 0 even when the underlying cargo test suite FAILED**. A "Background command completed (exit code 0)" notification is therefore NOT proof the suite passed.

**Why:** the digest-runner's own success (it produced a digest) is what surfaces as the tool exit code, decoupled from the wrapped command's real exit. Observed 2026-05-30: a broken `run_integration` test (`codex_bare_run_inside_owning_pane_fails_before_nested_dispatch`) failed under `make check`, yet the wrapper reported exit 0 — and a commit (`6f91beb2`) was pushed with the failing test as a result.

**How to apply:** to verify a Rust change, do BOTH:
1. Run `(make check; echo "MAKE_CHECK_EXIT=$?")` so `$?` captures make's real exit *before* rtk sees it, and assert `MAKE_CHECK_EXIT=0`.
2. Grep the output for real failures: `grep -E "result: FAILED|[1-9][0-9]* failed|error\[E"` (ignore `0 failed` / test-name substrings like `..._fails_...`).

Do not declare "make check green" on the wrapper's reported exit code alone. `cargo-nextest` is not installed locally, so `make test` runs plain `cargo test --workspace --all-targets`. Relates to [[feedback-precommit-testing]] and [[feedback-cargo-build-release-after-route-edit]].

**RTK also masks `git status` and node-script output (observed 2026-07-11, lazily-zig #lzzcpy release).** Through the RTK hook, `git -C <submodule> status --short/--porcelain` collapsed to a bare `ok` for repos that actually had modified/untracked files, and `node scripts/sync-coverage.mjs --check` reported exit 0 while the real script printed `7 target(s) stale` and exited 1. Both sent me down a wrong path (thought siblings were clean/synced when they were dirty/stale). **Fix: bypass the hook for status/verification reads — use `/usr/bin/git ...` (absolute path) and invoke node directly; `git diff --quiet <path>` under RTK also gave a false "modified".** Same root cause as below: the wrapper's own success decouples from the wrapped command's real output/exit. Also note tsift/RTK `source-read` and `cat` can serve **stale cached file content** — an earlier `cat coverage.json` showed a pre-edit version while disk was already updated; trust `/usr/bin/git diff` or a fresh direct `Read` over cached envelopes when a file may have changed.

**Re-confirmed 2026-07-19 (lazily-rs `#lzspecedgeindex` teardown-scope rename).** `make check` reported "completed (exit code 0)" while actually failing with `make: *** [Makefile:52: clippy] Error 101` — a stale `ctx.child()` call in `examples/child_context_spike.rs` that a `src/`-scoped rename missed. Grepping `result: FAILED|^error|Error [0-9]+` caught it; the exit code did not. **Additionally: the captured output file was compacted to 8 lines**, so grepping for which make steps actually ran (`lake build`, `benchmark-check`) returned nothing — you cannot confirm the run reached its final steps from the wrapper's log at all. When a verdict matters, re-run as `{ make check > /tmp/<name>.log 2>&1; echo "EXIT=$?" >> /tmp/<name>.log; }` and read that file directly. Lesson beyond RTK: **scope renames to the whole crate, not `src/`** — `examples/`, `benches/`, and `tests/` compile under `--all-targets` and are where a partial rename surfaces.

**RTK masks `git push` — it reports `ok (up-to-date)` for a push that did NOT happen (observed 2026-07-19, lazily-zig).** Two commits were local; `git push origin main` through the wrapper printed `ok (up-to-date)`; `git log @{u}..` still showed 2 unpushed and `origin/main` was still at the old sha. `/usr/bin/git push origin main` then pushed them for real. **This is the most dangerous variant in this file**, because it makes you report work as delivered when it is still only local — and unlike a masked test result, nothing downstream will ever contradict you. **Always push with `/usr/bin/git push`, and verify with `/usr/bin/git log --oneline @{u}.. | wc -l` returning 0.** After any session with multiple pushes, audit every repo the same way; one masked push in a batch is easy to miss because the others succeed.

**RTK's `diff` wrapper reports files as identical when they differ (observed 2026-07-19, lazily-js `#lzdartobservercow` fixture audit).** Comparing a bundled conformance fixture against its canonical source in `lazily-spec`, RTK's wrapped `diff` printed `[ok] Files are identical` for `crdt-tree/algebra.json` — while `cmp` and a parsed-JSON compare both confirmed a real difference in the `description` field. The drift was only caught because the comparison was re-verified by other means. **Never establish "these files match" through RTK's `diff`** — for fixture/mirror comparison use `cmp -s`, `/usr/bin/diff`, or a semantic compare (parse both and compare structures), and prefer semantic equality over bytes so reformatting does not produce noise failures. This is the most dangerous variant of the family so far: the others report a wrong *status* for work that ran, whereas this one asserts a positive factual claim about file contents that is false.

**RTK also masks clippy, AND local toolchain drifts behind CI (observed 2026-06-06, tsift #trt1p2 cycle).** `cargo clippy --workspace --all-targets -- -D warnings` run through the RTK hook prints a summarized `cargo clippy: No issues found` even when clippy actually fails — the real lint errors are swallowed. Compounding it: tsift CI's runner uses **rolling stable** (rolled to rustc 1.96.0), while the local toolchain was pinned older (1.94.0); `clippy::unnecessary_sort_by` got stricter in 1.96 and flagged three pre-existing `sort_by(|a,b| b.X.cmp(&a.X))` Copy-key reverse sorts in `packages/tsift-cli/src/commands/infra.rs` that 1.94 accepted — so local `make check` was green but CI's `clippy + test` job went red. To reproduce CI clippy locally: (1) `rustup update stable` to match CI's version (check the rust-X.Y.Z URL in the CI clippy error to see which version CI used); (2) run real clippy bypassing the RTK masking with `rtk proxy cargo +stable clippy --workspace --all-targets -- -D warnings`; (3) if it still finishes in ~0.1s it used cache — `cargo clean -p <crate>` (or touch sources) to force a real re-lint. Note `unnecessary_sort_by` only fires on Copy keys (suggest `sort_by_key(|b| std::cmp::Reverse(b.X))`); String-key single sorts and `.then(...)` compound sorts and `partial_cmp` float sorts do NOT fire.
