When a concurrent session has uncommitted WIP in `src/equityfundingsource-dev`, `deploy:worker` ships the **whole working tree** live.

**FIRST decide clean-worktree vs main-tree** — grep the *current live* browser bundle for the concurrent session's uncommitted-WIP markers (unique added string literals from `git diff` on their files):
- **Their WIP is NOT live** → deploy from a **clean worktree at HEAD** (below) to ship only your committed change.
- **Their WIP IS already live** (they deployed a dirty tree) → a clean-worktree deploy would **revert their live UI** (clobber). Instead, once their WIP is idle (check mtimes — not edited in the last few min) and compiles, **deploy from the main working tree** (`build:worker` from `app/equityfundingsource`, then `deploy:worker:no-migrate`): it's a superset (their live WIP + committed history + your commit), so it adds your fix without reverting anything. Verify live afterward that BOTH your markers AND their WIP markers are present. (Seen 2026-07-07: clean-HEAD deploy would have dropped `full-app-reveal-section`/`portal-modal-open` that the other session had shipped dirty.)

**⚠️ Never offer the user a "worktree isolation" deploy option when foreign WIP is in `lib/*` — it does NOT isolate the browser bundle.** Re-confirmed 2026-07-08: deployed my committed Deal Packet from a clean worktree at HEAD (symlinked `node_modules`), yet the live `index.browser-*.js` contained the other session's uncommitted `full_application_detail.tsx` markers (`use_reveal_section_`/`reveal_section_`/`editable_form_from_` — 5–7 hits each, all absent in HEAD). The worker/server bundle WAS clean (built from the worktree's `app/`), so `/dp/:token` + `deal_packet_links` shipped correctly; only the browser bundle leaked. Chasing it with a re-deploy is an unwinnable race while the other session deploys dirty trees (their own deploys ship the same WIP). Use **stash-in-main** from the start, or accept the leak and disclose it.

**⚠️ The clean-worktree recipe below is BROKEN for `lib/*` (UI) WIP — do NOT use it when the foreign WIP touches `lib/ui--browser--efs`, `lib/ui--server--efs`, or `lib/domain--server--efs`.** These are bun **workspace packages** (`workspaces: ["app/*","lib/*"]`) imported as `@btakita/ui--browser--efs`. Symlinking the main checkout's `node_modules` into the worktree (step 3) makes `node_modules/@btakita/*` resolve **relative to the symlink target = the main checkout's `lib/`**, so the browser build silently bundles the concurrent session's uncommitted `lib/` WIP even though the worktree's own source is clean. Verified 2026-07-07: deployed from a "clean" worktree at my commit, yet the live bundle contained the other session's `full-app-advance-link`/`full-app-reveal-section` (absent from HEAD, present only in their unstaged diff). The worktree is only truly isolated for `app/*` changes, not `lib/*`.

**The worktree + real `bun install` also fails — don't bother.** To dodge the symlink leak I tried `git worktree add` at my commit, then a real `bun install --frozen-lockfile` (not a symlink) so `@btakita/*` resolves to the worktree's own clean lib. `bun install` succeeded, but `bun run build:worker` then failed at `pack:worker`: `no complete CSS bundle found; ... static: none` — the rebuild-tailwind pipeline never emits the tailwind static CSS in a fresh worktree, so pack-assets can't assemble the worker CSS. Verified 2026-07-08. The main checkout builds fine because its CSS state is warm. Conclusion: **stash-in-main is the only reliable isolation for this repo**, even for `lib/*` WIP. Do not spend time on worktrees here.

**Shared file with BOTH your edits and foreign edits (e.g. `email/lifecycle.ts`).** When a concurrent session edited the *same file* you did (verified 2026-07-08: `email/lifecycle.ts` had my wire gating AND their `notify_lender_deal_packet_` + its `deal_packet_lender_email_` import), you cannot stash "their part" of one file, and `git add -p` is unavailable (no interactive flags). Surgical fix: (1) `cp` the mixed file to a backup; (2) `git checkout HEAD -- <file>` to reset it clean; (3) re-apply ONLY your edits with Edit; (4) commit your file (now HEAD+yours, no foreign); (5) `cp` the mixed backup BACK over the file so their edits return to the working tree (else their next build breaks — their code still imports the function you removed). After step 4 the working tree diff for that file is exactly their delta, which the stash-isolate below then handles. Removing their code from the shared file WILL break the whole-tree build until you restore it in step 5 — that's expected; your isolated deploy builds from HEAD (post-stash), not the mixed tree.

**Untracked foreign migration.** A concurrent migration (e.g. `0116_deal_packet_links.sql`) is untracked, so `git stash` won't move it and `cf:d1:migrate:remote` would apply it alongside yours. `mv` it to scratchpad before deploy, then `mv` it back after. Confirm with `d1 migrations list --remote` that only YOUR migration is "to be applied" before running deploy.

**Correct isolation when foreign WIP is in `lib/*` (stash-in-main, no worktree):** because your own change is already committed to HEAD, the main checkout's *only* remaining working-tree diff is the foreign WIP. So:
1. Snapshot the foreign WIP: `git diff > <scratchpad>/wip.patch` (safety net for pop conflicts).
2. `git stash push -m isolate -- <each foreign file>` (list only their paths; yours are committed so they're not in the diff). Main tree is now clean at HEAD+your-commit and `@btakita/*` resolves to the main checkout's own clean `lib/`.
3. From `app/equityfundingsource`: `bun run deploy:worker` (or `:no-migrate` if no new migration). Migration `cf:d1:migrate:remote` is idempotent — safe to include when you added one.
4. **Immediately `git stash pop`** to restore their WIP (minimize the window their work is missing).
5. Verify pop restored byte-identically: `git diff | diff - <scratchpad>/wip.patch` → identical. If pop conflicts (they edited during the window), `git checkout` the files and `git apply <scratchpad>/wip.patch`.
6. Verify live bundle has YOUR markers and NOT theirs.
Check their file mtimes first — if edited in the last few minutes the session is active and stash/pop may conflict.

**✅ Confirmed WORKING for `app/*`-only foreign WIP (2026-07-08).** Fixed `/admin/deals/:id` → Deal Pipeline modal redirect (`lib/portal/admin/routes.ts`, server-side). Concurrent session's WIP was four `app/equityfundingsource/lib/**` files (loan_management, repo, admin/routes, investor/deal_marketplace) — all in the **app package, none in workspace `lib/ui--*`**. Committed only my file, `git worktree add --detach <WT> 84002f8`, symlinked BOTH root + app `node_modules` and `.env`, `bun run build:worker` (CSS canary `md:grid-cols-3` present), `bun ./bin/cf-deploy.ts worker`. This is the case the symlink-leak warning does NOT apply to (foreign WIP not a workspace package). Left commit local/unpushed.

Clean-worktree recipe (only when their WIP is not live AND is confined to `app/*`):

1. Commit only your files (stage explicitly; leave foreign WIP alone).
2. `git worktree add --detach <WT> HEAD` under `src/` (not /tmp).
3. Symlink both `node_modules` (submodule root **and** `app/equityfundingsource/node_modules`) from the main checkout; copy gitignored `.env` (holds `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`), `.dev.vars`, `bun.lock`.
4. `set -a && . ./.env && set +a` then from `app/equityfundingsource`: `bun run deploy:worker:no-migrate` — the `:no-migrate` variant (defined only in app/package.json, not root) skips `cf:d1:migrate:remote`. Use it for UI-only changes so you don't apply another session's staged D1 migrations.
5. Verify live: fetch `<base>/index.browser-<HASH>.js` (hash from the build's pack-assets manifest `js_src`) and grep for your unique string literals. Real bundle is ~1.9MB; a transient ~36KB stub means mid-propagation — refetch.
6. Remove symlinks first, then `git worktree remove --force <WT>`.

**Pre-deploy clobber check (worker/server-only changes):** before deploying, `curl -s <base>/ | grep -oE '/index\.browser-[A-Z0-9]+\.js'` and compare to your clean build's `dist/worker/index.js` manifest hash. If they **match**, the concurrent session's uncommitted UI WIP is NOT live, so your clean deploy won't revert any live UI — only the worker's server logic changes. If they differ, the other session deployed WIP; coordinate before shipping. (For a server-only gate you can't easily behavior-test live — admin routes sit behind Cloudflare Access — so verify by grepping the built `dist/worker/index.js` for your unique string literals + confirm the fresh `Current Version ID` from wrangler.)

**Volatile shared tree → COMMIT your edit the instant it's written.** When the concurrent session runs `git stash`/`git reset --hard`/`git checkout .` (to clean their tree before committing, or to pop WIP), those ops act on the WHOLE working tree and **silently wipe or restore YOUR uncommitted edits too** — even edits to files they never touched. Verified 2026-07-07: my `full_applications.tsx` edits flip-flopped present→absent→present across consecutive reads as their stash cycles ran. Do NOT build/deploy/verify against uncommitted work in this tree — stage+commit your file in a single atomic Bash call (`git add <file> && git commit`) the moment the edit is done; committed changes are immune to their stash/reset. Then your dedup/fix survives and their next build (from HEAD) carries it.

**Deploy race → COMMIT is the durable fix, not re-deploying.** If both sessions are deploying the shared worker, each `deploy:worker` clobbers the other within seconds (last-write-wins), and you'll see the live `index.browser-<HASH>` flip to *their* hash right after yours + a transient 36KB/404 stub mid-propagation. Do NOT loop re-deploying — that's an unwinnable war. Instead: **commit your change to shared HEAD.** Once committed, the *other* session's next full `build:worker` (which builds from the working tree = committed files + their WIP) automatically includes your feature. So even when their bundle hash wins, grep it — your committed feature is in it. Verified 2026-07-07: after my deploy was clobbered twice, live bundle `GFZH6BDZ` was the *other* session's build yet contained my committed `SelectedLenderRequirementsNextStep` + endpoint because `202051f` was in HEAD. Deploy once to reclaim, verify your markers are in whatever hash is live (yours or theirs), then STOP.

Leave the commit **local/unpushed** — the superproject branch is shared; pushing collides with the concurrent session.
