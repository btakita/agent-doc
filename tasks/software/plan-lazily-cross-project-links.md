# plan: cross-project links in every lazily README

## Goal

Make `lazily-spec/README.md` the place you send someone who has just heard of
lazily, and make every other lazily README lead back to it. Today a reader
landing on `lazily-go` has no way to discover that eight sibling bindings, a
shared conformance corpus, and a Lean model exist.

## The family (12 public repos under `github.com/lazily-hub`)

| repo | role |
|---|---|
| `lazily-spec` | Language-agnostic wire protocol, feature matrix, and the canonical conformance corpus every binding replays. **The hub.** |
| `lazily-formal` | Lean 4 formal model — the neutral formal home every binding depends on equally. |
| `lazily-rs` | Rust — the reference implementation. |
| `lazily-py` | Python |
| `lazily-go` | Go |
| `lazily-kt` | Kotlin / JVM |
| `lazily-js` | JavaScript / TypeScript |
| `lazily-cs` | C# / .NET |
| `lazily-cpp` | C++ |
| `lazily-zig` | Zig |
| `lazily-dart` | Dart / Flutter |
| `lazily-react` | React / Preact bindings layered over `lazily-js` (not a separate language binding). |

**`lazily-html` and `lazily-interop` are NOT part of this set.** Their git
remotes point at `btakita/agent-loop`, not `lazily-hub` — they are workspace
directories, not published projects. Linking them would produce dead links.

## What each README gets

### 1. `lazily-spec/README.md` — the referral page

Add an **Implementations** section high in the file (after the intro, before
`## Feature Set`) carrying the full table above with links, each row naming the
language and linking the repo. Then a short **Formal model** line pointing at
`lazily-formal`, and a pointer from the existing `## Binding Conformance`
section to the per-binding repos so the parity table and the repo list are
reachable from each other.

The spec README already documents the feature matrix and conformance corpus;
this is about discoverability, not restating them.

### 2. Every other README — a `## The lazily family` section

Placed near the end, before any license/contributing footer. It contains:

- one line on what lazily is across languages,
- a link to `lazily-spec` described as the protocol + conformance corpus,
- a link to `lazily-formal` described as the Lean 4 model,
- the sibling table, with **the current repo shown in bold and NOT linked**
  ("you are here"),
- for `lazily-react`, an explicit note that it layers over `lazily-js`.

## Rules

- **Do not invent install instructions.** Several packages have known-blocked or
  in-flight registry publishes. Reuse whatever install/usage text the repo's own
  README already carries; if it has none, link the repo and say nothing about
  registries. A README that tells a reader to run a command that fails is worse
  than one that stays quiet.
- **Do not restate the feature matrix** in each binding. Link to
  `lazily-spec`'s `coverage.json`-generated table instead — it is generated by
  `sync-coverage.mjs` and hand-copies would rot immediately.
- **Do not touch the generated coverage tables.** `sync-coverage.mjs --check` is
  a gate in several bindings; edits inside the generated block will fail it.
  Keep the new section entirely outside any generated region.
- Match each README's existing heading level, tone, and link style.
- Relative links do not resolve across repos — use absolute
  `https://github.com/lazily-hub/<repo>` URLs.
- Run the repo's `make check` (or its README/link check if it has one) before
  committing. `lazily-py` has `run_readme`, which executes README code blocks —
  do not break it.

## Verification

- Every link resolves (`gh repo view lazily-hub/<name>` or an HTTP check).
- No repo links itself.
- `lazily-html` / `lazily-interop` appear nowhere.
- The repo's own gate stays green.
