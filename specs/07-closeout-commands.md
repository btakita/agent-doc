# Closeout Commands

This file covers binary-owned response persistence: commit boundaries, patch/write semantics, recovery, and post-write session validation.

## Harness-neutral closeout

The closeout/write path is shared by every harness. Claude Code may enter it
from a slash-command skill, Codex may enter it from a plain `agent-doc <FILE>`
prompt plus Codex hooks, and OpenCode may enter it from its command wrapper, but
the durable response boundary is the same: parse/validate the assistant
payload, mutate the document through the write pipeline, commit the snapshot,
and pass `session-check`.

No harness gets a private response patchback path. In particular, Codex direct
turns and the Codex Stop hook are recovery/backstop inputs to the same
`finalize` / `write --commit` machinery; they must not commit console text,
full-document transcript dumps, or editor `fullContent` replacements outside
that machinery. Harness-specific code may choose how to launch, resume, route,
or prove capabilities, but it may not change the closeout semantics.

## commit

`agent-doc commit <FILE>`

- Commits the saved snapshot, not arbitrary working-tree drift.
- Narrow self-heal is allowed only for agent-owned drift that preserves the redacted component structure, or for exchange-only already-committed historical response growth proven by `HEAD`.
- Plain user prompts must remain uncommitted.
- If `snapshot == HEAD` but the working tree still differs, `commit` must classify that state as later local drift rather than a missed patchback.
- If `snapshot == HEAD` while an active response capture still exists, `commit` must prove that the captured response body is present in the staged snapshot/`HEAD` before closing the cycle as already committed. A prompt-only `HEAD`-current snapshot with a missing captured response must fail closed and leave the cycle at `response_captured` for `agent-doc write --commit <FILE>` replay instead of logging `commit_already_current`.
- If that later drift is a follow-up prompt after an already-committed response, `commit` must say the no-op is not a full closeout for the follow-up prompt, name both `agent-doc <FILE>` and `agent-doc write --commit <FILE>` as the next commands, and log the benign `post_commit_user_follow_up` marker instead of `prior_patchback_without_response_body` or `out_of_band_write`.
- If `snapshot == HEAD` and the only working-tree difference is deletion of safe escaped conversation content outside `agent:exchange`, `commit` may adopt and commit that cleanup. If the same diff also contains a fresh prompt inside `agent:exchange`, the prompt must remain uncommitted for the next cycle.
- Direct assistant patchback in the working tree without a newer binary-owned cycle must fail closed.
- Historical self-heal must fail closed if typed components such as `status`, backlog, or pending changed, or if the repaired tail would still contain a bare prompt target.
- The command serializes the staging/commit critical section with a git-dir scoped advisory lock.
- For submodule-hosted documents, `commit` must carry the closeout through the parent repository gitlink commit. If the document snapshot is committed in the submodule but the parent `HEAD:<submodule>` pointer still differs from the submodule `HEAD`, closeout remains incomplete and recovery is `agent-doc commit <FILE>`.
- Successful post-commit cleanup must leave the committed blob, snapshot, and user-facing file in the same clean shape except for genuine later user edits.

## compact

`agent-doc compact <FILE> [--component NAME] [--message TEXT] [--tag NAME] [--commit]`

- Rewrites exchange or another component into a compacted summary/archive-pointer state.
- After writing the archive markdown, compact best-effort upserts that archive into `.agent-doc/archive-index.db`; indexing failure warns but must not roll back archive creation.
- For exchange compaction without an explicit message, the default summary must include an archive pointer plus a digest of the compacted exchange content. It must not duplicate live `agent:backlog`, `agent:queue`, or `agent:icebox` component content into `agent:exchange`.
- A committed response capture whose body is no longer in `HEAD` because exchange compaction archived it is still materialized when `HEAD` references a compact archive under `.agent-doc/archives/` and that archive contains the captured body; `stuck_captured_cycle` must not warn in that case.
- `#stuck-capture-queue-echo-false-positive`: the "is this captured response materialized in HEAD" check (`response_already_applied`) matches the captured response's normalized lines as one contiguous block. Queue consumption inserts a `> **Queue prompt:**` echo blockquote (`#queue-prompt-echo-in-response`) between the response heading and body, which would otherwise break that contiguous match and make `stuck_captured_cycle` falsely warn after every queue-consumed cycle. The normalizer therefore strips the `> **Queue prompt:**` echo blockquote on both the captured-response and document side before matching.
- `#stuck-capture-compact-false-positive`: that archive-suppression check is not durable on its own — if the referenced compact archive is later garbage-collected, the same capture would re-flag as stuck and re-suggest a `write --commit` that would re-inject an already-archived response. So `preflight` first runs `reconcile_compacted_committed_capture`: when a committed-cycle capture's body is absent from `HEAD` but proven present in a HEAD-referenced compact archive, it durably marks that capture `Discarded` (the same terminal state compaction assigns via `discard_captures_for_archived_responses`) and logs `reconcile_compacted_committed_capture`. Reconciliation advances only the active capture (loaded by the cycle's own `capture_id`), is idempotent once discarded, and after it runs `stuck_captured_cycle` sees a discarded capture and returns no warning even if the archive no longer exists.
- `#stale-capture-after-compaction-blocks-route`: when compaction archives response topics out of the live document, it must discard the capture sidecars whose `response_body` is contained in the archived text (intact or after prompt-prefix normalization), logging `capture_discarded_for_archived_response`. Containment against the *archived* text — not mere absence from the current document — is the safe discriminator, so a never-applied / genuinely pending capture is left intact. This prevents a later `route` drain / `validate_replay` from fail-closing with "captured response baseline no longer matches current document" (which otherwise forced a manual `reset --from-current --preserve-session`). The discard is best-effort and must never fail the compaction.
- `--commit` proves only that the compacted document state itself crossed the commit boundary; it does not also persist any later human explanation.

## patch

`agent-doc patch <FILE> <COMPONENT> [CONTENT] [--mode replace|append|prepend]`

- Deterministic named-component patcher for direct component mutation.
- Resolved component config may supply timestamps, size trimming, and pre/post hooks, but explicit CLI mode still controls append/prepend behavior.

## write

`agent-doc write <FILE> [--baseline-file PATH] [--stream] [--ipc] [--force-disk] [--origin ORIGIN]`

- Parses `patch:*` blocks from stdin, applies them against the baseline, merges with current disk content when needed, and saves snapshot/CRDT state.
- IPC-first write remains the default when the editor patch directory exists; `--force-disk` bypasses IPC.
- IPC ACK / sidecar success is not sufficient response proof by itself. Socket and file IPC success paths must verify that the materialized snapshot candidate contains the expected response-body probe before saving it as the snapshot or letting strict closeout commit it. If the editor consumes a patch but returns content that only contains a prompt, an unrelated sidecar, or a partial response heading, the write path must log `ipc_materialization_missing_response` and fall back or fail closed before the missing response can be marked committed.
- Insufficient IPC proof diagnostics must be explicit. Any no-ACK timeout, missing response-body probe, unacknowledged live exchange edit, live prompt drift, or duplicate-prompt ACK rejection must log `ipc_proof_insufficient` with `invariant=<exact failed invariant>` and `recovery=<next recovery path>`. Preflight and session-check interruption messages must surface the latest matching IPC proof diagnostic so operators see the failed invariant and recovery command path without digging through the raw ops log.
- **Typed closeout recovery instruction (`#closeout-repair-churn`).** The scattered "try `finalize` / `write --commit` / `commit`" recovery chain is collapsed into one classified state with a single recovery command. `flow::closeout::classify_closeout_recovery_state` maps the live cycle/capture/HEAD condition to one of `clean`, `open_cycle`, `missing_response_body`, `escaped_template_patch`, `direct_response_patchback`, `boundary_only_drift`, `nested_parent_pointer_stale`, `open_empty_preflight`, `queue_metadata_drift`, `sidecar_visible_drift`, or `unsafe_user_content_drift`, and `CloseoutRecoveryState::recovery_command` returns the single command for that state. `session_check::closeout_recovery_hint` renders `Recovery [<state>]: <command>` for every closeout guard message instead of a static line, so an operator/agent sees one typed next action. The recovery *mechanisms* already exist (`PatchbackShape::EscapedComponentMarkers` fail-closed, `write --commit` direct-patchback absorption, `complete_required_closeout` parent-pointer retry); this is the unifying classifier. **All eleven states now have precise detection (`#closeout-recovery-state-machine`).** `direct_response_patchback` is detected via `session_check::detect_bypassed_response_write` (a visible `### Re:` / `## Assistant` response inserted into the working file outside the binary write path), guarded against the `git::commit`-recoverable jb-cache-conflict-cancel shape so it is not misread as a manual patchback; recovery is `write --commit`. `nested_parent_pointer_stale` is detected via `git::submodule_pointer_drift` when the document itself is clean (snapshot == HEAD == working) but the submodule HEAD is ahead of the parent repo's recorded pointer; recovery is `agent-doc commit`. Both are checked in `classify_closeout_recovery_state` after the missing-body checks (direct-patchback before the generic content-drift fallthrough so the response-specific recovery wins over `unsafe_user_content_drift`; nested-pointer just before `clean`).
- **One-command recovery apply with authoritative-side determination (`#recursive-repair-apply` / `#recovery-drift-authoritative-side`).** `flow::closeout::apply_closeout_recovery` (CLI: `agent-doc repair --apply-recovery <FILE>`) performs the *unambiguously safe* recovery in one call. `open_empty_preflight` abandons the empty probe cycle; `boundary_only_drift` commits the boundary / answered-prompt-prefix artifact. `queue_metadata_drift` and `sidecar_visible_drift` are auto-applied only when `metadata_drift_authority` proves the direction: because the recovery already requires byte-identical *content* components (exchange / backlog / review / icebox / done), the only durable state the metadata diff can destroy is an active queue continuation. `queue_continuation::live_continuation_head` derives, from each side's document string, whether it carries a live `queue_active` continuation (a ready, non-fenced/non-time-gated head). A continuation present in HEAD but dropped (or re-headed away) by the local side cannot have been legitimately consumed — consumption always surfaces as response/content drift — so **HEAD is authoritative and the local drift is restored from HEAD** (the live-observed spurious `queue_active:false` working-drift class); otherwise the local side is committed forward. Distinct live continuation heads on both sides with no consuming response are genuinely ambiguous and return `NotApplied` with the recommended manual command. `unsafe_user_content_drift`, `open_cycle`, `missing_response_body`, and the reserved states always fail closed because they need a preserved response, not a metadata operation.
- IPC snapshot adoption must not absorb prompt-bearing or post-exchange scratch/comment drift that appeared after the preflight baseline from ordinary socket/file ACK content or file-read fallback content. When those proof sources contain user-owned `agent:exchange` prompt/content edits, tracked component edits outside `agent:exchange` such as a live `agent:queue` prompt, or ordinary text outside `agent:exchange`, that is absent from the agent-owned `content_ours` response image, the write path must log `flow_event flow=document_mutation stage=ipc_snapshot_adoption outcome=blocked reason=live_prompt_drift_after_preflight`, save the snapshot from `content_ours`, and leave the live drift visible in the working tree/editor for the next cycle. The later commit staging pass must not treat that same blocked drift as absorbable `status`, backlog, or queue drift. Socket `already_applied` is the narrow exception below because the editor is explicitly reporting that the response is already in the live buffer.
- IPC ACK content remains a whole-buffer observation, not a whole-buffer authority. If socket/file ACK sidecar content introduces extra response-aware user-prompt copies relative to the agent-owned `content_ours` image, the write path must log `flow_event flow=document_mutation stage=ipc_snapshot_adoption outcome=blocked reason=prompt_duplication_in_ack_content`, save the snapshot from `content_ours`, record the adoption block so later commit staging cannot absorb the bad sidecar, and repair the visible duplicated buffer through the guarded disk repair path. The duplicate-prompt count must ignore prompt-like text inside assistant response blocks so normal answers that quote user wording do not trigger the guard.
- Socket `already_applied` ACKs are also snapshot-bearing IPC success, but the snapshot may come from disk only after proof. If the current disk buffer is equivalent to `content_ours`, persist `content_ours` as before. If the current disk buffer differs but contains the materialized response-body probe, adopt the disk buffer as the snapshot after response-block and prompt-artifact dedupe, repairing the visible file to that same deduped content when necessary; this preserves concurrent user edits and prevents `HEAD`/working-tree divergence. If the current disk buffer does not contain the response probe, do not save stale `content_ours`; log `ipc_proof_insufficient invariant=disk_missing_response_probe recovery=file_ipc_fallback` and fall through to file IPC.
- **Typing-during-finalize verification marker (`#6cmx`/`#wy0y`):** when the socket `already_applied` path detects the live buffer diverged from `content_ours` with prompt drift (the operator typed into the document while finalize was writing), the write path logs an explicit `finalize_typing_during_write file=… patch_id=… typed_delta_bytes=… response_present=… resolution=content_ours_adopted` ops-log line alongside the lower-level `ipc_socket_already_applied_live_buffer_diverged … prompt_drift=true`. `typed_delta_bytes` is the live-vs-`content_ours` byte delta (the operator's keystrokes) and `response_present` confirms the assistant response is still materialized. This makes a typing-during-finalize repro a single greppable verification signal (was it exercised, did the response survive intact) without enabling the JB plugin's debug `setText` logging, which needs a reinstall. Keep this aligned in `write.rs` and this spec.
- **Late fallback patch rejection:** Once a cycle reaches `Committed`, any delayed IPC/file fallback patch for the same cycle must be rejected. The write path must check `cycle_state::load(file)?.phase` before applying fallback patches, before disabled full-content fallback cleanup, and while polling a file IPC patch for consumption; it must clean up leftover `.agent-doc/patches/<hash>.json` files after successful closeout. The stream IPC timeout path is part of that same invariant: if it writes locally and commits before exiting with `EX_TEMPFAIL`, it must remove the queued fallback patch immediately and leave a claimed-patch sentinel for watchers that already observed it. IPC payloads must include the current `cycle_id` so the plugin can reject stale patches. Late fallback rejection logs must include document path, cycle id, and patch id. This prevents a delayed file-watcher recovery from re-dirtying an already-committed document with stale duplicate response content.
- **Accepted conflict replay repair:** If accepting a JetBrains File Cache Conflict after `commit_success` replays a stale editor/cache payload, `session-check` must classify the state as an accepted-conflict replay when `dedupe(current)` matches committed `HEAD` modulo transient `(HEAD)` and boundary markers. The next preflight must remove the duplicate response from the working tree, save the repaired snapshot, and avoid a redundant commit because the repaired document is already in `HEAD`.
- **Dropped exchange-prompt guard (`#exchange-prompt-dropped-on-merge`):** When a user types a new prompt into `agent:exchange` while an editor holds `ipc.sock`, the IPC ack can carry a stale `content_ours` buffer that predates the prompt. The `live_prompt_drift_after_preflight` guard already adopts `content_ours` (snapshot stays at `content_ours`; see the concurrent-user-prompt rule), but a post-commit disk diff cannot reliably catch the loss because the editor may overwrite the disk prompt via IPC buffer convergence before `session-check` reads it. To make the data-loss class fail closed regardless of that race, the write path must **record the dropped user prompt-bearing exchange line(s) at adoption time** (the divergent candidate still carries them) into cycle state (`dropped_exchange_prompts`, ops-log `dropped_exchange_prompt_recorded`). `session-check` then runs a `dropped_prompt_guard` that interrupts when any recorded dropped prompt is still absent from the committed `HEAD` exchange, and clears the marker once the prompt reaches `HEAD` (resolved on a later cycle). The guard reads persisted adoption-time evidence, not the live disk tail, so it is immune to the editor-overwrite race. Full source-level prevention (converging the editor buffer to the merged disk content instead of re-asserting the stale buffer) remains the shared plugin-protocol work tracked under `#adoc-queue-ipc-buffer-divergence`.
- **Late-IPC committed-response over-application repair (`#duplicate-response-after-commit`):** A late IPC reposition / stale-patch replay can re-insert a response that already reached `HEAD` into the working tree — possibly wrapped in redundant `<!-- agent:boundary:* -->` markers and **non-adjacent** to its original (the consecutive-only `dedupe(current)` collapse misses this shape, so the generic `detect_bypassed_response_write` guard would otherwise misclassify it as a manual direct patchback and `write --commit` would dead-end with `empty response — nothing to write`). `session-check` must instead classify the state as a committed-response over-application when the working tree is `HEAD` plus strictly more **duplicate** response blocks: identical non-response scaffold (modulo blank lines and boundary markers) and the same set of distinct `### Re:` blocks as `HEAD`, with no new or lost response content. Detection compares the response multiset and scaffold against `HEAD` directly rather than relying on consecutive adjacency. When recognized, the next preflight must restore the committed `HEAD` content over the working tree and snapshot (logging `late_ipc_response_overapplication_repaired`) and avoid a redundant commit because the repaired document is already in `HEAD`. Any genuine new response content, lost response content, or scaffold drift must fall through to the normal patchback guard.
- **Exchange write diagnostics and duplicate prompt repair:** Every write path that touches `agent:exchange` must append an `exchange_write_diagnostic` ops-log line with writer pid/executable, source, write mode, patch id when available, cycle id, before/after content hashes, live-exchange drift, prompt-duplication, and prompt-normalization flags. Direct disk writes, socket IPC, file IPC, IPC timeout fallbacks, and guarded disk repairs after disabled full-content IPC attempts all participate. Final template reconciliation, content-ours normalization fallback, socket/file IPC snapshot paths, and snapshot-staged commit closeout must pass through canonical duplicate-prompt artifact repair before saving the snapshot or committing. That repair removes adjacent duplicate response blocks, exact already-answered prompt tails after the latest boundary, generated post-exchange duplicate prompt comments without baseline/snapshot/current-visible ownership proof, extra copies of prompt lines that were already present in the before-content, and adjacent live prompt prefix variants; it logs `duplicate_prompt_artifact_repair` with a per-artifact report while preserving the existing narrower logs such as `ipc_prompt_duplicate_repaired`, `post_exchange_duplicate_prompt_comment_removed`, and `live_prompt_prefix_variant_repaired`. Commit pre-stage repair is narrower than response write repair: it only repairs in-exchange prompt duplicates against the snapshot, collapses adjacent prefixed/raw copies of the same prompt line, updates the snapshot only when the repaired working tree is prompt-prefix-equivalent to the snapshot, and logs `commit_pre_stage_prompt_duplicate_repaired`. The scanner must be response-block aware: a prompt line quoted in the assistant response is not a duplicate prompt to remove and must not authorize post-exchange comment scrubbing. IPC timeout fallbacks and ack-content normalization fallbacks must adopt an already-visible editor response only when normalized `base -> content_ours` response insertion hunks are contained in the current `agent:exchange`; raw line-overlap counts are not sufficient proof, and prompt-prefix-only normalization plus boundary/comment churn do not count as required response hunks. Final template reconciliation and IPC snapshot dedupe may scrub duplicate or near-duplicate prompt text from ordinary post-exchange HTML comments only when the same user prompt is already present outside assistant response blocks in `agent:exchange` and the duplicate comment line was not already present in the pre-response baseline/snapshot or the visible current document used for the mutation, while preserving the ordinary HTML comment container itself, and log `post_exchange_duplicate_prompt_comment_removed` on write paths. Preflight and route pre-dispatch cleanup must preserve ordinary post-exchange comment bodies already visible before cleanup; they may still remove exact duplicate answered prompt tails inside `agent:exchange`. Editor-visible normalization has no baseline ownership proof, so it must preserve ordinary post-exchange comments. Cleanup must also remove exact duplicate answered prompt tails that sit after the latest `agent:boundary` inside `agent:exchange`, preserving the earlier normalized prompt block and response while logging `duplicate_answered_exchange_prompt_tail_removed` on write/route/preflight paths. Multiline ordinary comments are scrubbed line-by-line only for non-owned duplicate lines; a fuzzy duplicate match for one prompt line must not delete unrelated scratch, separator, log-triage lines, or an owned scratch line in the same comment. After safe comment scrubbing, route and closeout paths must fail closed if duplicate or near-duplicate prompt residue remains in freeform post-exchange Markdown outside tracked components, because arbitrary Markdown cannot be deleted safely without ownership proof. Ordinary scratch comments remain outside `agent:exchange` and are not prompt-bearing drift.
- **Terminal lifecycle idempotency:** Once cycle-state or capture-state reaches `Committed`, later repair/replay/no-op bookkeeping for the same terminal cycle must not rewrite the persisted lifecycle record, downgrade it to an open phase, or re-log `capture_committed_after_replay`. A new user-visible turn must start a new preflight cycle before recording new response lifecycle evidence.
- **FlowCore closeout transaction:** Closeout command paths pass through `flow::closeout` for the strict terminal transaction: commit, snapshot convergence retry, parent gitlink verification, terminal cycle-state proof, `session-check`, and fallback-patch cleanup. The stages remain pre-write guard, patchback parse, document mutation, snapshot convergence, pre-commit guard, commit, terminal guard, and session-check. The implementation emits typed `flow_event` records for commit completion, document-mutation parse outcomes, strict pending-capture / pending-done guard blocks, repair recovery boundaries, and committed-cycle late-fallback rejection. Future closeout fixes should extend those typed events instead of introducing independent proof strings.
- **FlowCore active-typing visible-write guard:** Direct disk writes that mutate the session markdown, including template, stream, IPC timeout fallback, repair replay, queue consumption, pending normalization, compact exchange, and direct `agent-doc run` responses, must pass through `flow::document_mutation` before saving the snapshot or replacing the visible file. If the shared typing indicator does not reach idle within the bounded debounce wait, the write fails closed before snapshot or document mutation and logs a `flow_event` with `stage=pre_write_guard` and `reason=visible_write_typing_defer_active_typing:<source>`.
- **Pre-write current-content proof:** Response write paths that already computed a merge from the current document must re-read the visible file after the typing guard and before snapshot/document mutation. The guard must also compare any editor live-buffer digest sidecar against the expected disk content so an idle but unsaved JetBrains/VS Code buffer cannot be overwritten by a direct disk write such as compact exchange. If the file or live-buffer digest differs from the content used for the merge, the write fails closed and logs `flow_event stage=pre_write_guard reason=visible_write_current_changed:<source>` plus `visible_write_deferred_current_changed` or `visible_write_deferred_live_buffer_changed`, preserving late scratch-comment or live-typing edits for the next cycle instead of committing a stale merge.
- **Full-content IPC disabled end-to-end:** The first-party binary must not emit whole-document editor replacements (`fullContent` socket/file IPC). Before any payload is emitted, the binary must still reject documents with explicit template frontmatter, legacy template/stream mode, or any `agent:*` component marker and log `full_content_ipc_scope_rejected scope=<scope>`. For otherwise eligible no-component append fallbacks, repair redelivery, or operator mutations, the binary logs `full_content_ipc_disabled`, returns `false`, and lets the caller use the guarded disk/snapshot path. The terminal committed-cycle guard still runs before this disabled-path return so stale fallback patch files are cleaned up and claimed. Editor plugins must also reject or delete any legacy/foreign `fullContent` payload without applying it, so stale patch files cannot overwrite live typing even when they were produced by an older sender.
- **Full-content receiver/static guard:** Production CLI, JetBrains, and VS Code receiver code may mention the `fullContent` wire field only for parser DTOs, null/empty rejection branches, disabled-path diagnostics, or legacy source-buffer proof helpers. Static regression tests must reject any first-party CLI `fullContent` payload emission and any receiver path that passes `patch.fullContent` to visible whole-document write APIs such as IntelliJ `Document.setText`, VFS `setBinaryContent`, or VS Code `WorkspaceEdit` full-range replacement.
- **Full-content IPC scope:** Normal template response writes must prefer component patches, normalization-only template writes must use `normalize_prefix_lines` without `fullContent`, IPC dedupe repairs must use guarded disk repair when no narrow editor patch exists, and operator compact exchange must use guarded direct write. Source-buffer proof fields remain diagnostic-only for legacy payloads; they are not authorization for the CLI or plugins to perform a whole-document editor replacement.
- **Cycle 1779845677327 regression:** If a post-exchange scratch HTML comment is edited during finalize or compact and contains prompt-preset/directive text such as `#spec-test-build-install-commit-push` or `dispatch #spec-test-build-install-commit-push`, that text stays user-owned. Closeout must not send `fullContent`, duplicate the prompt/response, move the ordinary comment into `agent:exchange`, drop the directive-looking lines, or save a shorter snapshot through `snapshot_absorb`; IPC snapshot adoption must fall back to `content_ours` and log `ipc_snapshot_adoption_blocked reason=live_prompt_drift_after_preflight`.
- **Post-IPC-block snapshot absorb guard:** Once a cycle logs `ipc_snapshot_adoption_blocked`, later commit/status staging for that same cycle must not convert any divergent live disk body into a new snapshot via `snapshot_absorb`. The closeout stages the existing `content_ours` snapshot and leaves the divergent live buffer visible for the next cycle, logging `snapshot_absorb_blocked_after_ipc_snapshot_adoption` instead of treating the divergence as safe out-of-band exchange/status/pending growth.
- Final parsed responses must be durably captured before any document mutation once they survive strict pre-write guards.
- Compatibility normalization may rewrite one legacy list-shaped backlog/pending patch through the granular pending primitives before capture, but unsupported shapes still fail closed before `response_captured`.
- Destructive `patch:todo` replacements are blocked when they would shrink an existing checklist surface.
- Template-patch response materialization proof uses the applied patch body, not the `<!-- patch:* -->` wrapper comments, when validating IPC sidecars, committed `HEAD`, and compact archives. A marker-bearing response that parses to zero patch blocks must fail before response capture rather than logging `0 template patches found` and creating a stuck captured cycle.
- Session-document `write --commit` shares `finalize`'s strict closeout contract.
- Strict `write --commit` with empty stdin may recover instead of failing when the document already contains an agent-doc-owned visible response from an interrupted `response_captured` / `write_applied` cycle. That recovery adopts the visible response into the snapshot and continues through the normal commit/session-check boundary.
- JB File Cache Conflict cancel recovery must treat a visible already-present response as authoritative only after proving the working tree matches the snapshot modulo transient markers. The recovery commits that response once, clears stale pending response sidecars, marks the active capture terminal, refreshes the capture `file_hash` / `snapshot_hash` to the recovered document state, and must leave `session-check` green without replaying a duplicate response or duplicate template scaffold.
- Empty stdin with only valid pending mutations, such as `agent-doc write --commit <FILE> --pending-add "..."` or `agent-doc write --commit <FILE> --done <id>`, is a valid pending-only repair closeout. The command must commit those pending mutations and must not fail after mutating the document solely because no assistant response body was supplied.
- The `committed_without_response_body` guard (`#codex-final-response-not-written`) must only fire when the cycle actually committed new binary-owned content this turn. A **no-op commit** — `last_event = commit_already_current`, where the closeout found the snapshot already equal to `HEAD` (for example a `finalize --done <id>` whose reaped item was already reflected in `HEAD`, leaving the document byte-identical) — committed nothing, so there is no committed-work-without-a-response shape and the guard must skip it (logging `committed_without_response_body_guard_skipped_noop_commit`). Firing on a no-op commit deadlocks the cycle: the recommended `write --commit` recovery is itself a no-op (no response body to write, nothing to commit), so a re-running closeout poller re-interrupts every pass forever. A real missed response still commits actual side-effect content (`last_event` `commit_success` / `commit`) and continues to fail closed.
- The no-response skip above does not authorize hiding live queue work. `#nochange-after-stall-breadth` requires `session-check` to fail closed when a committed no-response repair/reap-only cycle recorded an active `agent:queue` `do [#id]` head and that id remains both queued and open in `agent:backlog` without same-cycle done/gate/reap/kept-open proof. In that shape, the closeout was bookkeeping only, not a completed queue turn; operators must run the queued head or explicitly resolve/defer it before a clean no-change verdict. Non-terminal stale-open cycles (`preflight_started`, `response_captured`, `write_applied`) likewise remain interruptions even when document and snapshot bytes match.
- Empty stdin with no recoverable visible response and no pending mutations must fail before any commit/session-check closeout attempt. It must leave live prompt drift in the working tree for the next response cycle instead of committing that prompt as a repaired assistant closeout.
- Bare session-document `write` is not a terminal success path: if it preserves a response and leaves the cycle open at `response_captured` / `write_applied`, the command must fail closed with recovery intact instead of returning success and waiting for a later `agent-doc commit`.

### Write-path invariants

- Template/CRDT retries and IPC timeout fallbacks must adopt an already-visible response instead of appending or CRDT-merging a duplicate block, including when the user is concurrently typing new prompt text inside `agent:exchange`.
- Template/CRDT disk writes, IPC timeout disk fallbacks, and repair replays must prove the visible file still matches the just-merged current content immediately before saving snapshots or replacing the document. A late edit in an HTML scratch comment or exchange tail is a retry blocker, not merge input that may be overwritten by the stale write.
- Final template reconciliation must run the duplicate-prompt repair before the visible document write for direct disk, CRDT, IPC timeout fallback, and repair replay paths, not only after an editor IPC sidecar succeeds.
- IPC sidecar success paths must run adjacent response-block dedupe on the exact content they will save as the snapshot. If dedupe changes that content, the working tree and editor repair payload must use the same deduped document before commit.
- The commit transaction must re-run adjacent response-block dedupe on the staged snapshot content while holding the commit lock. A successful closeout must never rely on a later `agent-doc dedupe` or cleanup commit to remove a duplicate response block that was visible before staging.
- Prompt-prefix normalization for append-mode exchange comes from the shared prompt-bearing classifier, not ad hoc line-shape guesses.
- IPC sidecar verification and post-commit working-tree prompt-prefix repair must preserve duplicate prompt-target occurrences by count; one earlier prefixed `spec-test-...` line must not mask a later bare duplicate.
- IPC sidecar verification fallbacks must merge the current disk content with `content_ours` against the explicit pre-response baseline, re-apply `normalize_prefix_lines` to that merged fallback before saving it as the snapshot, and repair the working tree to the same normalized fallback. When the rejected editor sidecar differs only by prompt-prefix normalization, the binary must first re-deliver a narrow socket or file IPC repair (`patches: []`, `unmatched: ""`, `normalize_prefix_lines`, `reposition_boundary: true`) after proving the visible buffer still matches the exact rejected sidecar. Full-content redelivery is disabled for every scope; after narrow repair failure or ineligible non-normalization repairs, the binary must fall back to guarded disk repair and log the scope rejection or `full_content_ipc_disabled` instead of handing the editor a whole-document replacement. A bare prompt-target line in fallback content, plugin-written disk content, or a stale editor buffer must not become the next committed closeout baseline, and concurrent non-exchange user edits such as scratch-comment deletion must not be restored by the repair. When this fallback path runs because a sidecar stripped a required prompt prefix, the ops log must record `sidecar_normalization_fallback reason=prefix_divergence`, an `ipc_repair_decision` with patch id, hashes, prefix counts, and duplicate-prompt count, and either a narrow repair result or a full-content disabled/scope skip before `sidecar_normalization_fallback_repaired_working_tree`; `#normfallback` in `tasks/agent-doc/agent-doc-bugs2.md` covers that diagnostic and repair contract.
- The `tasks/software/tsift.md` duplicate-content incident is the named regression fixture for response-fallback redelivery: if repair planning captured an older duplicate/bad editor state and the user typed a new prompt into the visible buffer before redelivery, full-document IPC must skip socket/file emission and leave that live buffer untouched. If the bad editor state is still current, the same redelivery still skips full-document IPC because the path is disabled and uses guarded disk repair.
- The `tasks/professional/equityfundingsource.md` post-exchange typing incident is the named finalize replay fixture for live prompt drift during closeout. Deterministic tests must replay the same scratch-comment typing window through socket IPC, file IPC with ACK sidecars, stale file-IPC timeout cleanup, and forced direct-disk finalize so the live prompt remains visible for the next cycle while `HEAD` and the saved snapshot stay on the assistant-owned `content_ours` response.
- Prompt-prefix overrun protection is diagnostic-only. If a normalization cycle would apply more than `MAX_NORMALIZE_USER_LINES` prefixes, the binary must log `normalize_threshold_exceeded action=passthrough` and leave content unchanged for the typed repair/closeout path to handle; it must not force-commit the working tree from inside prefix normalization.
- The repair/redelivery transition logs are intentionally temporary high-signal observability. Keep `ipc_repair_decision`, `sidecar_normalization_fallback*`, narrow-repair result logs, full-content disabled/scope skips, and duplicate-prompt counts until local full-suite verification and the tmux/CI leg have stayed green across representative socket IPC, file IPC, and disk-fallback runs. Cleanup may then reduce success-path noise, but must preserve blocked/stale proof, corruption, duplicate-prompt, and visible-write diagnostic events.
- IPC snapshot adoption runs a default-on forensic detector for the `#ipcfullprompt` corruption shape (`#ipcfullprompt-recur2`). Independently of the fail-closed snapshot guards (which protect what is committed), every socket and file IPC adoption compares the live editor buffer (the candidate, captured before the guards replace it) against the pre-response baseline and logs `ipcfullprompt_corruption_suspected` to `ops.log` — plus preserves the baseline and candidate under `.agent-doc/logs/ipcfullprompt/` — whenever a previously-committed `### Re:` response block is deleted or duplicated in the candidate. The detector (`agent_doc_core::ipc_corruption::detect_response_block_corruption`) ignores brand-new response headings and the working-tree-only `(HEAD)` annotation, and is detection-only: it never changes the adoption decision. This captures the not-reliably-reproducible editor-side full-document corruption without any manual editor debug opt-in. The adoption hook also runs `detect_duplicated_scaffold` on the candidate (no baseline required): the full-tail duplication shape — captured live in `brandon-cinquegrana.md` — copies the post-exchange scaffold (close marker + Queue/Backlog/Icebox) around an in-progress prompt, leaving two `<!-- /agent:exchange -->` markers, which the `### Re:`-keyed response-block check does not see. It flags any canonical structural component marker (counted only on its own line, so inline mentions do not inflate it) that appears more than once.
- IPC timeout disk fallbacks must never commit a response before the prompt text it answers. If CRDT merge or stale-boundary placement leaves the just-written response block before prompt-bearing exchange text, the write path must reorder that prompt text before the response and move the boundary after the response before snapshot/commit; if the response/prompt order still cannot be proven, the write must fail closed instead of reporting success. `agent-doc repair` must apply the same ordering repair when a pending/captured response is already visible in the document.
- `content_ours` prompt-prefix normalization must preserve committed `HEAD` prefix state before adding prefixes for new prompt targets; assistant response tail lines that already exist in `HEAD` without `❯ ` must stay bare even when a later user prompt is inserted directly below them.
- Post-commit prompt-prefix repair must use opt-in prompt-run criteria inside agent response blocks. A line being already prefixed with `❯ ` is not sufficient evidence by itself; repair may leave a response block only for an explicit normalization target or a line that independently looks like a prompt, question, imperative, or soft request.
- Explicit-baseline writes must classify live disk drift against the pre-response baseline before the response is present. If a concurrent user prompt is added after preflight but before `finalize` / `write --commit`, the committed closeout snapshot stays at `content_ours` and the post-commit `session-check` must interrupt with the unresolved `prompt_target` instead of treating the just-written response as an answer to that later prompt.
- For strict template/CRDT append-mode writes to `agent:exchange`, the explicit baseline must not be allowed to subtract committed exchange history. If `--baseline-file` lacks exchange content already present in `HEAD`, `finalize` / strict `write --commit` must rebase patch application onto `HEAD` before computing `content_ours`, IPC payload baselines, IPC snapshots, timeout fallback snapshots, or commit-staged snapshots. Later live user drift is still compared against that effective pre-response base and remains outside the closeout commit. The write path must log `explicit_baseline_rebased_to_head` when it takes this repair path.
- Template/CRDT writes, IPC fallback writes, and `agent-doc commit` must fail closed before mutating or staging when the persisted snapshot is significantly larger than the visible file and the difference is not classified as a safe binary-owned mutation. This shape indicates a manual cleanup with stale `.agent-doc/snapshots/<hash>.md` / `.agent-doc/crdt/<hash>.yrs` state; recovery is `agent-doc reset --from-current <FILE>` so future writes rebuild sidecars from the current visible markdown instead of resurrecting old content.
- When an explicit-baseline template/CRDT write answers a prompt target that was typed as raw text inside `agent:backlog` / legacy `agent:pending`, the write path must remove only those newly-added prompt-target lines from the backlog after merging the response. Normal tracked backlog edits, pending state changes, and unrelated concurrent non-exchange edits must remain intact.
- Concurrent non-component user edits, including markdown or HTML comment tails directly below `agent:exchange`, must remain visible in the working tree/editor buffer and stay outside the assistant closeout commit unless the user explicitly asks to commit that edit. The same rule covers compacted exchange summaries where the live prompt sits after a compacted `### Session Summary` and boundary inside `agent:exchange` while the scratch comment is being edited below the closing marker. Closeout may scrub stale post-exchange HTML comment text only when that duplicate prompt text is absent from both the pre-response baseline/snapshot and the visible current document read before the response write. If equivalent duplicate prompt residue remains as ordinary post-exchange Markdown after comment cleanup, closeout fails closed instead of guessing whether to delete or relocate it.
- Carried-forward formatting directives from historical `❯ ...` prompt blocks must be re-injected into new agent prompts when they still read as active document-level requirements.
- Orchestrate-origin template writes may synthesize a patch-free, clean single assistant response into `agent:exchange`, but patch-bearing orchestrate writes must include `patch:exchange` and must not carry unmatched text outside patch blocks. Plain orchestrate responses with transcript prompt lines, `## User` / `## Assistant` headings, multiple `### Re:` replies, or full-document component markers are invalid.
- Template writes fail closed if live conversation content would end up outside `agent:exchange`, including the inter-component gap between the exchange close marker and later components such as backlog, except for the narrow duplicate-close / duplicate-open repair shapes the binary knows how to normalize safely. A duplicated template scaffold between two exchange close markers is repairable only when the segment is pure scaffold. If that duplicated scaffold is mixed with live prompt text, the write path fails closed and logs a typed document-mutation flow event instead of moving or deduplicating that prompt text automatically.
- Template patchback shape classification belongs to `flow::document_mutation` and runs before visible document mutation in template, stream, IPC, and repair replay paths. Patch markers with no closed patch blocks are `malformed_patch`; patch blocks plus unmatched output are `mixed_output`; a patch-free response that instead carries fully-formed raw `<!-- agent:NAME -->` component blocks is `escaped_component_markers`; transcript-shaped dumps are not valid template patchbacks unless a command explicitly owns a narrow normalization path. Orchestrate-origin plain-response synthesis and malformed plain-response rejection also use this same document-mutation gate.
- `escaped_component_markers` must fail closed before any snapshot save or commit. This is the raw-template form (`<!-- agent:status -->` / `<!-- agent:exchange -->` blocks piped to `finalize` / `write --commit` instead of `<!-- patch:* -->` blocks); committing it as plain text escapes the markers into the live exchange (`#closeout-repair-churn`). The typed diagnostic must point to the supported `<!-- patch:exchange -->` form or to rerunning `agent-doc write --commit <FILE>` to absorb an already-visible `### Re:` response, and must leave the document, snapshot, and `HEAD` unchanged. Boundary markers (`<!-- agent:boundary:HASH -->`, no close marker) and markers inside code fences are not component blocks and do not trip this guard.
- Boundary markers are binary-owned. The write path removes stale boundaries, inserts a fresh end-of-exchange boundary, applies the response, and re-inserts a fresh boundary at the new exchange end.
- Exchange append replies must bind to the oldest compatible unresolved prompt block rather than skipping earlier prompts still ahead of the old boundary.
- **Prompt-edit-resilient anchoring (`#patchback-prompt-edit-resilience`).** The anchored exchange append locates the insertion point by exact match of the baseline (`original_doc`) unresolved tail against the current document — the fast path. When the operator edits the prompt between baseline capture and closeout (a typo fix, or adding/removing the `❯ ` prefix), that exact match no longer holds. Instead of failing closed (which forces manual baseline-drop + prefix-repair retries), the append falls back to **position-based** anchoring when the unresolved tail is a single prompt block: because the boundary has already been repositioned to the end of the component, the sole (possibly edited) prompt is the trailing content of the user region, so the response anchors at its end. Only the genuinely ambiguous multi-prompt-edit case fails closed, and it does so with an actionable `re-run agent-doc preflight to refresh the baseline` diagnostic rather than the prior cryptic "failed to locate unresolved prompt tail" error.
- Response-replay / stale-cycle recovery hash matching is immune to queue churn. The normalized hashes used to decide whether a `preflight_started`/committed cycle is safely recoverable neutralize the `agent:queue` component body, its opening-tag attributes (for example `auto`), and the `queue_active:` frontmatter flag before hashing, because queue maintenance rewrites those on essentially every cycle independently of the response body (which always targets `exchange`/`output`). Store-side (`cycle_state`) and compare-side (`repair`) normalization must stay identical so queue-only churn produces a hash match while a genuine response-body change still fails closed. This keeps the recurring `stuck_captured_cycle` symptom from wedging an IPC-owned document (#adoc-queue-ipc-buffer-divergence root cause #4).

## finalize

`agent-doc finalize <FILE> [write flags...]`

- Strict happy-path closeout for session responses.
- Validates git-backed context before mutation, runs the normal write pipeline, and only enters the commit closeout after the write path succeeds or performs an explicit empty-response recovery. Pre-write guard failures must leave the document, snapshot, queue, and active cycle open for retry instead of committing an unanswered cycle, and must emit a typed FlowCore `closeout/pre_write_guard` blocked event for operator forensics. Successful closeout still fails unless the final cycle state is `committed`.
- When the active prompt is synthesized from `agent:queue auto` and the visible document itself has no queue-head diff, `finalize` must still consume the queue head after a successful write if the captured response heading explicitly targets the queue item or its `#id`. A response to an unrelated prompt already present in the baseline must keep preserving the queue head.
- For submodule-hosted documents, strict closeout also verifies the parent repository pointer reached the new submodule commit; a best-effort pointer update failure must interrupt instead of reporting success.
- When strict closeout crosses the latency budget, it must surface phase timings for git commit, retry, cycle-state, session-check, and cleanup work in a `closeout_latency` diagnostic so operators can tell which closeout layer delayed response durability.
- When `--baseline-file` points at a missing hash-keyed preflight baseline because the session document was moved after preflight, closeout must retry the current document hash's migrated baseline before failing. This preserves the explicit baseline contract across `git mv` / rename migration.
- Empty normalization-only template payloads are invalid; the response must contain real response-body proof.
- The same pre-write pending-capture, backlog-required, and pending-done gates apply here before the document mutates.
- `--done <id>` is a tracked-work mutation for `do #id` closeout, so it satisfies pending-capture guards without requiring a synthetic `--pending-add` or `<!-- no-pending-capture -->`. If the id was already reaped into canonical `agent:done`, into the repo-relative external `.done.md` archive named by `agent:done archive=...`, or recorded as resolved in the active cycle, the flag is idempotent and emits a warning instead of failing the closeout. Legacy `agent:backlog-done` and `agent:pending-done` markdown components are not accepted as completed archives; run `agent-doc migrate` to rewrite them.
- If a response appears to complete a tracked backlog/icebox item whose live line has a malformed checklist prefix, strict closeout must fail before writing the response. A damaged line such as `_- [ ] [#id] ...` is document corruption, not proof that the item is absent or complete.
- A bare `compact exchange` request blocks ordinary finalize/write closeout and must route through `agent-doc compact <FILE> --commit` instead.

## repair

`agent-doc repair <FILE>`

- Repairs open `response_captured` / `write_applied` cycles, deduplicates already-applied responses, and can adopt a visible response already present in the live document when the snapshot still lags behind.
- Visible response adoption is not limited to no-cycle manual repair. If an open agent-doc cycle proves the interrupted write path already owned the response, repair adopts that response rather than reporting it only as a direct patchback bypass.
- The same repair path also handles stale `preflight_started` cycles when the hashes or safe historical `HEAD` proof make that deterministic, and it may auto-close an otherwise-empty `preflight_started` cycle after the bounded stale timeout when no response capture exists. If that stale empty cycle has unresolved prompt-bearing drift such as `do #id`, repair marks the old cycle `abandoned` without writing a placeholder response; the prompt remains visible for the next fresh preflight cycle. Recent empty prompt-bearing cycles still fail closed with retry/restart guidance instead of being abandoned.
- Historical capture replay is narrow: it requires either an active capture artifact or a matching orphan prompt target in the live exchange.
- Transcript-shaped or full-document-dump captured payloads must fail closed and be parked under `.agent-doc/repair-blocked/`. Patch payloads may carry only known replay guard comments such as `<!-- no-pending-capture -->` outside patch blocks, and plain progress commentary before the first patch may be stripped so the valid patch body can replay.
- No-pending repair still runs transcript canonicalization, completed-backlog reap, safe escaped-conversation repair (including the exchange-to-backlog gap case), safe duplicate-close repair, and deterministic stale-boundary repair when applicable.
- Explicit `repair` must fail closed, not print a false clean `No pending response found`, when `session-check` would still block the document after those no-pending repairs. In particular, when a committed historical patchback can be repaired from `HEAD` but later prompt-bearing user drift still remains, `repair` must surface the same interruption instead of downgrading the blocked document to `Noop`.
- For git-backed docs, repair must not stop after updating the document or snapshot. The same command must carry the recovered closeout through commit.

## preflight

`agent-doc preflight <FILE>`

- Runs interrupted-cycle recovery, repair, commit, claims-log drain, linked-doc inspection, diff computation, and HEAD read in one binary-owned step.
- Before diffing, preflight must not auto-compact the exchange just because the session is large or churn-heavy. Session-accretion heuristics remain advisory only, and any future automatic compaction/reload path must require an explicit `agent_doc_auto_compact` opt-in in document frontmatter or project `.agent-doc/config.toml`. When that opt-in is absent, `session_accretion.guidance` must not emit imperative `Run agent-doc compact <FILE> --commit` text that an agent could auto-execute; it must instead emit gated phrasing that names the missing opt-in and tells the agent to ask the user before compacting.
- If the pre-diff tmux layout check detects missing window index `0`, preflight attempts the base-index repair immediately in the active tmux session, re-runs the layout check after a successful repair, and reports only remaining layout issues. It must not defer this repair behind a consecutive-detection counter; when automatic repair cannot run, stderr must name the explicit repair command.
- Planning must not convert advisory session-accretion signals, including repeated no-op closeout churn, into a `compact` handoff unless the prompt or document explicitly requests compaction.
- Open cycle states are `preflight_started`, `response_captured`, and `write_applied`; `committed` and `abandoned` are terminal.
- If `route --dispatch-only` saved a busy-actor queued dispatch into the snapshot (`queue_active: true`, `agent:queue auto`) but that snapshot has not reached `HEAD`, preflight must commit the saved route-owned snapshot before diffing. Later visible user edits on top of that queued snapshot remain unstaged and must be surfaced as the next prompt diff; the recovery must not absorb those edits into the queue snapshot commit.
- Boundary-only / `(HEAD)`-only churn is normalized back to `no_changes`.
- If the file diff is empty but the active harness prompt still contains body text after `agent-doc <FILE>`, preflight synthesizes an in-memory diff from that prompt body.
- Preflight must fail closed before diffing when the snapshot/file pair already looks like an uncommitted assistant closeout with no recoverable cycle left to explain it.
- Explicit backlog targets extracted from prompt presets are resolved relative to the project root. If a relative target begins with the current project directory name, that redundant prefix is stripped before falling back to a non-existent doubled path.
- Before any document-mutating recovery, pending maintenance, commit, or duplicate-residue cleanup, preflight must wait for the shared editor typing indicator to become idle. If the indicator remains active through the bounded wait, preflight fails closed instead of writing a cleaned document or sidecar state over a live editor buffer.
- Prompt-tail relocation before diff must ignore ordinary HTML comment bodies after `agent:exchange`, even when those comments contain prompt-looking text or preset names. Scratch-comment text must remain outside exchange instead of being moved into the live prompt tail.
- Known prompt-preset or dispatch-looking text inside ordinary post-exchange HTML comments is non-executable scratch content. Preflight must preserve it outside `agent:exchange`, must not add it to `prompt_presets_requested`, and must emit a visible warning that the comment is a user note unless moved into `agent:exchange` or `agent:queue`.
- Preflight and route pre-dispatch cleanup preserve ordinary post-exchange HTML comment bodies already visible in the file, even when those comments duplicate or near-duplicate a prompt already present in `agent:exchange`. They must not move comment text into exchange, must not advance the snapshot to include a live prompt, and must leave comment cleanup to write/IPC paths that can prove the duplicate line is generated residue rather than user-owned scratch content.
- Preflight must remove exact duplicate answered prompt tails while they are still after the latest `agent:boundary`, before the commit step can reposition that boundary to the exchange end. Route pre-dispatch must run the same cleanup before submitting an editor reroute. This cleanup is narrower than prompt-tail relocation: every non-comment tail line must match a contiguous prompt block immediately before an existing response heading earlier in `agent:exchange`.
- The `baseline_file` emitted by preflight must be written from the same stable visible-document content used to compute the diff. A response baseline captured before final debounce/stability checks is invalid because editor replay can otherwise leave `baseline_file` cleaner or older than the prompt-bearing document the agent is answering.

## session-check

`agent-doc session-check <FILE>`

- Verifies that the latest response cycle reached a terminal committed state and that no likely direct assistant patchback bypassed the binary-owned write path.
- Fails on open cycle states, uncommitted visible `### Re:` / `## Assistant` patchbacks, hidden `snapshot != HEAD` closeout drift, or committed-cycle exchange drift that appends a prompt+response pair or other new assistant response content.
- Preflight/sync closeout-drift guards reuse the same exchange-drift detection for promptless response-body drift, so a prior OpenCode/Codex/direct-exec response body that is visible only in the working tree cannot be hidden behind a generic clean snapshot or postponed to the next manual commit. Prompt-bearing user edits still flow into the next normal preflight diff.
- Fails when a committed submodule document snapshot still leaves the parent repository submodule pointer uncommitted, naming the submodule path and prescribing `agent-doc commit <FILE>` recovery.
- Fails after a committed closeout when the working tree still contains prompt-bearing user edits that were added concurrently with the write and therefore are absent from the committed snapshot.
- Fails after a closed cycle when the live `agent:exchange` tail ends with a prompt-looking block and no later assistant response, even if the prompt already matches the committed snapshot. This prevents direct/manual implementation commits from counting as closeout when the response patchback was skipped.
- Plain `content_edit` drift without a new prompt target or response patchback is not an unstarted closeout by itself; session-check must leave that to the next normal preflight diff instead of forcing another finalize cycle after a committed turn.
- The active Codex post-commit drift guard is scoped the same way: exchange-only content edits with no unresolved prompt target are allowed to wait for the next preflight diff, as are answered-prompt marker / `(HEAD)` / boundary churn paired with backlog metadata wording drift. Typed-component drift outside that promptless closeout metadata envelope, fresh prompt targets, or response patchback markers still fail closed.
- May self-heal only narrow exchange-only already-committed historical drift proven by `HEAD`.
- Must fail closed when the repaired tail would still include a bare prompt target or typed-component drift.
- Direct-patchback diagnostics may report a bare prompt target only when that
  target appears before the newly inserted response heading. Prompt-like prose
  inside the response body after `### Re:` / `## Assistant` remains assistant
  content and must not be surfaced as a missing `❯ ` user prompt.
- Optional closeout sidecars such as cycle-state, capture, startup-miss, and ops-log files are advisory; if one disappears between discovery and read, session-check treats it as absent state instead of surfacing a transient `ENOENT`.
- Runs the pending-capture, pending-done, backlog-shadow, backlog-replay, completed-item reap, snapshot-vs-HEAD, and parent-submodule-pointer closeout guards after a committed cycle.
- Fails closed when a live backlog/icebox line looks like a tracked checklist item with an id but is not parseable as a canonical pending item. This prevents malformed prefixes from hiding an open item from the pending-done guard.
- The pending-done guard reads completion signals from the response body, including `### Re: do [#id]` headings paired with later commit/verification/push evidence. It must not treat same-cycle pending mutation text as completion proof, and ids explicitly kept open by `--pending-edit`, `--pending-gate`, `--pending-ungate`, `--pending-reorder`, or gate-type edits are excluded from missing-`--done` warnings.
- **Synced-queue exclusion from `expect_done_or_gate_ids` (`#queue-sync-auto-pending-done-guard-misfire`).** When a backlog/icebox `queue=sync|append|prepend` attribute (`#backlog-queue-sync-attr`) auto-populates an active queue in the same cycle, the freshly-synced `do [#id]` lines surface as diff additions and would otherwise be recorded as cycle `do`-directives — making `pending_done_guard` demand every synced backlog item be resolved in the populating cycle. Preflight excludes only the backlog→queue ids newly inserted by that maintenance pass from `expect_done_or_gate_ids`; any id already present in the pre-sync queue, including the consumed queue head, remains an expect-done target. Without a `queue` sync mutation, directive accounting is unchanged.
- **Partial `do [#id]` closeout narrowing (`#do-id-partial-closeout-state`, WARN-only).** When a `do [#id]` turn ships a repo phase — the response carries a shipped signal (committed + pushed) — but the same response says live deploy / sync / verification / approval work remains, and a directed id is still `[ ]` open in `agent:backlog` (not done/reaped this cycle), `check_partial_closeout_state_guard` emits a WARN advising the agent to narrow the backlog item + queue head to the next phase via `--pending-edit` (or `--pending-gate` when only review/external validation remains), so the visible item describes the next action instead of the original full task. This guard is WARN-only by design — it must never block the closeout, because the auto-queue drain depends on this path — and is suppressed by a `<!-- no-partial-closeout-guard -->` response marker once the item is already narrowed. Remaining work (per `tasks/agent-doc/plan-do-id-partial-closeout-state.md`): per-id complete/gated/partial outcome tracking so the guard can distinguish a narrowing `--pending-edit` from a bare keep-open, an opt-in strict mode, and queue convergence that carries the revised next-phase prompt forward.
- **Blocked `do [#id]` follow-up capture (`#blocked-closeout-followup-capture`).** `--pending-gate <id>` is reserved for implementation-complete work awaiting review/external validation. When a `do [#id]` cycle instead gates a directed id out of `agent:backlog` (`pending_gated_ids`, still present in `agent:review`) while the response signals the work is blocked / still needs future action — a tight phrase list (`remains blocked`, `next steps to complete`, `must remove/expire …`, `awaiting approval before …`, `deliberately delete`, …) co-occurring with `#id` in the same response paragraph — `check_blocked_closeout_followup_guard` fails closed under `pending_done_guard` strict mode (WARN under `warn`). It is satisfied by any of: keeping the id open with `--pending-edit "<id>=…"` (id stays in `agent:backlog`, recorded as kept-open), adding a new follow-up via any `--pending-add*` primitive (`pending_added_this_cycle`), an explicit "no additional backlog follow-up is needed because …" justification phrase, a `<!-- no-blocked-followup-guard -->` / `<!-- no-pending-done-guard -->` response marker, or marking the id `--done`. The paragraph-scoped id tie keeps an incidental blocked phrase about unrelated work — or the `### Re:` heading that always names the id — from firing the guard. This is distinct from `#do-id-closeout-open-backlog` (target left `[ ]` open in backlog) and `#do-id-partial-closeout-state` (shipped+pushed phase still carrying full-task text, WARN-only).
- **Queue-audit partial-completion advisory (`#queue-audit-partial-completion`, WARN-only).** A queue-completion audit ("which queue items are complete?") should classify each row as complete / partially complete / not-started, naming the completed substeps and the exact remaining condition for partial rows, instead of collapsing meaningful partial progress into a blanket "none complete." Per the binary-vs-skill rule that per-row classification is natural-language judgment, the binary only flags the unambiguous collapse: `check_queue_audit_partial_completion_guard` emits a WARN when the committed response is about the queue, makes a blanket none-complete claim (`\b(none|no)\b … complet(e|ed)`), cites ≥2 distinct substep completions (`is complete`, `was clean`, `passed`, …), and never frames anything as "partial." WARN-only — never blocks closeout — and suppressed by a `<!-- no-queue-audit-guard -->` marker. The richer per-row state table and split/narrowing recommendation are response-contract guidance (skill/spec), not deterministic row classification.
- **Gated-phase split advisory (`#gated-followup-split-enforcement`, WARN-only).** When a directed `do [#id]` cycle keeps a tracked item open (`--pending-edit` / `--review-edit` / `--pending-gate`, recorded in `pending_kept_open_ids`) whose body enumerates multiple gated/remaining phases — the word "phase" plus ≥2 short parenthesized phase markers (`(2b)`, `(3)`, …) framed by a gating signal (`gated`, `remaining`, `live-verify`, `awaiting`, `still needs`) — but does not break those phases out into discrete child backlog IDs (≥2 distinct `#child` references other than its own id and the `#agent-doc-bug` preset tag), `check_gated_phase_split_guard` emits a WARN advising one child backlog ID per actionable phase (sibling of `#blocked-closeout-followup-capture` and the SKILL "one backlog ID per actionable phase" rule). It is WARN-only by design — it never blocks closeout — and is suppressed by a `<!-- no-gated-phase-split-guard -->` response marker when the phases are intentionally one unit.
