Operator correction 2026-06-22 (agent-doc-bugs2 dogfood): **"The CPC + Supervisor should be able to drive `make install` + `agent-doc admin recycle`. Plugin already installed."**

I had been repeatedly telling the operator to *manually* `make install` + `admin recycle` + install the JB/VS Code plugins after every committed agent-doc change. That framing is WRONG:

- The **supervisor auto-install** (`run_supervisor_auto_install` in `project_controller.rs`, fired from `start/idle_watch.rs` ~L1072 when source is newer than the installed binary, gated by `supervisor_auto_install_enabled` / `AGENT_DOC_SUPERVISOR_AUTO_INSTALL`) **rebuilds + installs the committed source and recycles onto the fresh binary at the next turn/idle boundary**. ops.log proves it: `supervisor_auto_install_started` → `supervisor_auto_install_succeeded next=recycle_onto_fresh_binary` fired repeatedly through the session, keeping the binary current commit-by-commit. So committed code goes live on its own — I do NOT need to tell the operator to `make install`.
- The **JB plugin is already installed**; stop listing "install the plugin from disk" as a per-change blocker. The plugin hot-reloads the cdylib by mtime, and the auto-install path refreshes it.

**Why:** the whole point of the dogfood supervisor is autonomous refresh. Treating install as a manual operator gate created false "stale binary, install the batch" handoffs when the supervisor was actually installing all along.

**How to apply:** after committing an agent-doc change, trust the supervisor auto-install/recycle to bring it live at the next boundary; only the genuine **live editor/pane eyeball** stays operator-gated. The one real failure mode to watch: the auto-install runs `cargo build --release`, which `make check` (cargo-nextest, DEBUG) does NOT run — a release-only break (or a transient build failure) makes `supervisor_auto_install_failed ... cargo build --release ... exit status: 101` and STALLS the binary at the last good commit. So after a test-bearing change, also confirm `cargo build --release` is green (not just `make check`), and grep ops.log for `supervisor_auto_install_failed` if recent commits aren't going live.

**SECOND failure mode — FALSE success (version-gated no-op), confirmed 2026-06-26:** `supervisor_auto_install_succeeded next=recycle_onto_fresh_binary` can fire **dozens of times in a loop while the installed binary never actually advances**. Live case: source HEAD `28740e76` (`fix(op-capture): memoize current_base_hash to fix per-keystroke typing slowdown`) was committed but the version stayed `0.34.49`; preflight kept emitting `stale_install: ~/.cargo/bin/agent-doc ... predate(s) source commit 28740e76` yet auto-install reported success every idle boundary. The version-equality gate sees `0.34.49 == 0.34.49` and treats it as already-current, so the real rebuild + recycle is a no-op — the running route-owned supervisor + JB cdylib keep executing pre-fix code. This is what surfaces to the operator as the live CRDT/typing symptom cluster ("you keep deleting my queue items / hard to type / CPU thrashing / line duplication") AND the complaint "I'm confused which sessions run a stale supervisor — make it auto-restart automatically." **Recovery: `make install` in `src/agent-doc` (uses `cargo install --force`, which is NOT version-gated → really rebuilds + installs binary + cdylib), then `agent-doc admin recycle <FILE>` (re-execs the route-owned parent at the idle boundary).** Confirm: preflight `stale_install` warning clears and `~/.cargo/bin/agent-doc` mtime advances. Diagnose by trusting the preflight `stale_install` warning OVER the looping `auto_install_succeeded` lines — the warning compares source-commit vs binary, the success log only compares versions. The real code fix (queue it): gate the auto-install on source-commit / binary-vs-source freshness, not the version string, so a no-version-bump fix still promotes.
