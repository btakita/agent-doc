The recurring overnight wedge chain — `finalize` → `live_prompt_drift_after_preflight` → appends `ipc_proof_insufficient` diagnostic + `content_ours` recovery → next `finalize` refused ("previous cycle still `preflight_started`, unresolved prompt_target: ipc_proof_insufficient ... no response exists to replay") → `--force-disk` → `direct_response_patchback` + `postcommit_worktree_check match=false` → recover via `git checkout HEAD -- FILE` + `agent-doc reset --from-current --preserve-session` — is **NOT staleness**. Root-caused 2026-06-26 (agent-doc-bugs2 dogfood, subagent w/ file:line cites):

**The recycle is a true `execve` (`start.rs` `CommandExt::exec()`) that discards ALL in-memory state; the fresh supervisor reloads doc+queue from disk per cycle — there is no long-lived in-memory CRDT to "go stale."** So both the operator's "stale supervisor" hunch and my earlier "stale in-memory CRDT" framing were mechanically wrong. The real defect: **the recycle gate had no agent-doc-cycle interlock.** `supervisor_recycle_action` / `do_recycle` gated only on the coarse harness whole-turn marker `turn_active` (TTL 3600s), NOT on the agent-doc `preflight→finalize` cycle phase (`cycle_state::is_open()`) or in-flight IPC (`ipc_socket::inflight_connection_handlers()`). The agent-doc cycle runs *inside* one harness turn. So a recycle — especially the `#supautoinstall` recycle-onto-fresh-binary firing right after a finalize commits a source edit — could `execve` AFTER preflight took its snapshot but BEFORE finalize commits, tearing down the in-flight IPC listener; the next finalize sources a divergent disk-fallback snapshot → `ipc_snapshot_would_absorb_live_prompt_drift_after_preflight` (`write.rs`) raises the drift. **The recycle firing mid-cycle is the bug — not "needing to recycle a stale supervisor."**

**Why:** the cure is the OPPOSITE of "recycle mid-turn": *don't let the recycle fire mid-cycle*. Make the `execve` wait for a quiescent boundary (cycle committed + IPC drained).

**How to apply:** when you hit `live_prompt_drift_after_preflight`, don't chase a "stale supervisor" / don't `admin recycle` to fix it (that's what *caused* it) — recover via `checkout HEAD` + `reset --from-current --preserve-session`. **Phase A fix landed 2026-06-26** (agent-doc main `27bf61a6`, installed): a `cycle_open` interlock (`cycle_state::is_open() || inflight_connection_handlers() > 0`) defers EVERY recycle arm (auto / `explicit_admin` / `write_wedged` / `EscalateKillRelaunch` / `#wd40` fresh-binary flush) → `DeferCycleOpen`, logging `supervisor_recycle_deferred_cycle_open`; the `execve` can only fire once the cycle is committed, so the drift is *impossible* (gated in review pending operator live zero-drift eyeball). **Phase B is queued (`#midturnresumeb`, plan `tasks/agent-doc/plan-midturn-recycle-resume-wedge.md`):** the `#durablerecycle` checkpoint (`cycle_state.rs:486`) is written-but-NEVER-consumed-to-resume-a-turn — actively consuming it on a fresh boot (idempotent vs the surviving-child path) is the full "restart reliably restarts the turn"; plus a deferred-too-long escalation so a never-closing cycle can't starve the recycle. Refines [[feedback_stale_binary_supervisor_causes_live_crdt_edit_bugs]] (that's a genuinely stale BINARY — distinct from this mid-cycle-recycle timing bug) and [[feedback_post_commit_worktree_drift_checkout_head_recovery]].
